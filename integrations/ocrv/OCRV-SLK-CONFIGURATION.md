# OCRV integration for SLK 4.4.2

OCRV is the registered Checker, normally bound to Qwen3.8-Max. It owns independent D1 and may hold SLK TOKEN only at the registered Checker stages; it does not own D0, D2, plan revision, role recovery, BI, or Temporal decisions.

Before a Run, verify the installed OCRV version and update need, the managed wrapper/capability hashes, headless execution, native-activity evidence, actual model/harness/endpoint, and the preparation-frozen token/time limits. Current work uses one complete candidate preview followed by one full D1 review and the severity-based closed classifier; historical segmented evidence remains eligible only for its closed recovery routes. A finding is not automatically FAIL, provider thinking is not formal evidence, and historical fixed line/file/background limits are advisory only. Full candidate evidence remains local and traceable.

OCRV is a fresh-launch stateless harness rather than a persistent chat Session. Before its first review, the role registry uses the resolved native `runtime_root` together with host identity and endpoint version as the truthful harness locator; each actual review Session is recorded later by native start/result evidence and does not silently rewrite the role identity. OCRV has no arbitrary prompt/chat entry, so do not fabricate an eight-answer model response: use native `ocr llm test`, installed wrapper/capability hashes and the isolated headless preview/review preflight as its tool-bound conformance evidence.

Normal work is `Checker → Worker → Checker`. OCRV records the real D1 result, then its managed post-D1 suffix sends PASS to the next Required CELL or final `D2_READY`, and sends a formal FAIL to Supervisor. The host—not OCRV text—verifies native start and commits TOKEN. A first formal FAIL may return one bounded Supervisor directive to the same Worker. A second consecutive formal FAIL must stop ordinary rework and go to Supervisor for a versioned CELL split; OCRV does not split, self-retry, lower acceptance, or create a third ordinary round. INCOMPLETE, transport/tool failure and duplicate receipts do not count as formal FAIL.

All helper processes are headless. Compact native activity is atomic and bounded; original output stays referenced by path/hash. Do not infer activity from a title, visible text, old PID, BI, TOKEN or stale session data.
