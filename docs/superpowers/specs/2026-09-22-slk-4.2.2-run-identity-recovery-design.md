# SLK 4.2.2 Run Identity Recovery Design

Date: 2026-09-22
Status: Owner-approved design baseline

## Problem

SLK 4.2.1 can preserve a correct predecessor/successor chain, but it has no legal state operation for converging several already-created Run roots when an older Run's Supervisor credential is irrecoverable. The existing `RUN_SUPERSEDED` event is insufficient: it requires the source Run's current role credential and, without the reciprocal predecessor link created by `init-run`, the read model correctly classifies the cross-root link as `ORPHANED_IDENTITY`.

The same live Run may also need to adopt the compatible 4.2.2 runtime contract without pretending that it was originally created under that version. Direct SQLite edits, invented credentials, free-text version claims, and another replacement Run are forbidden.

## Decision

SLK 4.2.2 adds two narrow Supervisor administration operations. They do not discover history, select the canonical Run, alter engineering facts, move `SLK TOKEN`, or create work. The Supervisor supplies every Run identity, the exact frozen snapshots, and an Owner authorization evidence identity. The state core only validates and records that decision atomically.

### `reconcile-run-identities`

The canonical Run's current Supervisor credential authorizes one request containing:

- a unique receipt ID and the canonical Run ID;
- a non-empty, duplicate-free list of explicit source Run snapshots;
- an exact canonical snapshot;
- closed Owner authorization evidence: source task/thread identity, message identity, content SHA-256, decision code, and occurrence time;
- the reason and operation time.

Each snapshot binds Run ID, project ID, method version, state, closure state, event count and latest event ID, TOKEN sequence and holder, role count, evidence count, and current identity fields. The transaction rejects a missing or changed fact, cross-project source, canonical-as-source, already closed or reconciled source, missing current canonical Supervisor authority, unknown fields, empty evidence, duplicate source, or conflicting receipt replay.

On success it marks only the named sources archived with closure `superseded`, points them to the named canonical Run, and appends an immutable reconciliation receipt containing the exact request and payload hash. It does not create or rewrite predecessor links and does not edit old events, roles, credentials, TOKEN history, evidence, CELL state, D0, D1, or D2. An identical receipt replay is idempotent; the same receipt ID with different content is rejected.

The read model treats a cross-root source-to-canonical pair as legitimate only when the current database facts exactly match an accepted reconciliation receipt. Those sources project as `HISTORY`, while the canonical Run remains `CURRENT`. A bare `superseded_by_run_id`, title similarity, boundaries text, or partial receipt never receives this exception.

### `adopt-method-contract`

The same canonical Supervisor may submit a second, separately idempotent request containing:

- an adoption receipt ID and Run ID;
- exact current Run snapshot;
- exact `from_version` and supported `to_version`;
- the Owner authorization evidence object;
- an optional required reconciliation receipt ID;
- closed compatibility assertions for unchanged topology, roles/endpoints, TOKEN, CELL/D1 history, and absent active Overwatcher;
- the reason and operation time.

Schema migration preserves `origin_slk_version` and keeps `slk_version` as the effective method contract shown by existing readers. Adoption from 4.1.1, 4.2.0, or 4.2.1 to 4.2.2 is supported only when the Run is open, current, snapshot-matched, has no active Overwatcher, and any cited reconciliation receipt belongs to that Run. The transaction appends an immutable adoption receipt and updates only the effective version. It does not revise the plan, move TOKEN, or alter engineering history.

`bind-overwatcher` rejects a Run whose effective method contract does not support the active Overwatcher contract. For the RC08 acceptance Run, Owner has chosen a fixed 240-second baseline cadence; real events may trigger an earlier extra cycle, while the next proactive cycle retains the fixed binding cadence.

## Data and projection

Schema v6 adds:

- `runs.origin_slk_version`, backfilled from the pre-migration `slk_version`;
- append-only `run_identity_reconciliation_receipts`;
- append-only `run_method_adoption_receipts`.

Both receipt tables reject update and delete at the SQLite boundary. Query and Markdown export expose compact receipt metadata and origin/effective versions. BI remains read-only and gains no mutation command.

## Security and authority

- Only the current canonical Supervisor credential can invoke either operation.
- TOKEN ownership is not required because these are Run identity administration operations, not engineering events; neither operation can move TOKEN.
- Owner authorization evidence uses a closed decision code and exact external message identity plus SHA-256. The core records the evidence identity but does not infer Owner intent from prose.
- The state core never searches by title, project name, time, or boundaries text and never chooses source or canonical Runs.
- Existing source credentials remain untouched. An unavailable credential is not forged, replaced, or silently revoked.

## Failure behavior

Every mismatch fails before mutation. Operations are one SQLite immediate transaction. A partial source list cannot be inferred or completed automatically. Unsupported version adoption, stale snapshots, missing evidence, conflicting replay, or active Overwatcher returns a closed error and leaves all Runs unchanged.

## Validation

Tests cover ordinary and optimized Python paths plus Rust state behavior:

- missing, malformed, or wrong-decision Owner evidence;
- wrong project, title-derived selection, duplicate source, canonical-as-source, stale event/TOKEN/count/identity snapshots;
- partial, conflicting, and idempotent receipts;
- exact five-Run fixture producing four `HISTORY` and one `CURRENT` without predecessor fabrication;
- unchanged source events, roles, credentials, TOKEN, evidence, CELL/D0/D1/D2 and canonical T010;
- adoption preserves origin version, changes only effective version, requires a supported transition and cited reconciliation receipt, and rejects silent or repeated conflicting adoption;
- pre-adoption active-Overwatcher binding rejection and post-adoption eligibility;
- append-only SQLite triggers, query/BI schema, root/install identity, Manifest, version, and release hygiene.

## Non-goals

4.2.2 does not add an orchestrator, history classifier, automatic merge, background repair, heartbeat, scheduler, daemon, new Agent, new Run, or product migration. It does not modify LCaS. R3B Supervisor remains responsible for its canonical decision, source list, snapshots, Owner evidence, and later execution of the accepted commands.
