## 三组问题，而不是重复累计缺陷数

### 一、材料：代码视图与运行时证据的地址空间没有接通

- **不是仅仅长路径或 Windows 权限。** 实际 OCRV 是 `v1.12.12 (182898c)`；其 [FileReader](https://github.com/alibaba/open-code-review/blob/182898c/internal/tool/filereader.go) 在 commit/range 模式只执行 `git show <ref>:<path>`，`file_find` 也查 Git 树，而 D0 日志在固定候选之外。只读复现将实际原件改为 119 字符的相对位置：磁盘文件存在，Git 读取仍 exit128。缩短路径、提高模型能力或重复同一指针都不能连接两个地址空间；也不能为了读日志静默改成 workspace 验收、改变固定候选。
- **补充说明被适配时丢掉。** `role_host.py` 把管理说明和原件位置写入 `D1_MANAGEMENT_RETURN` 外层；`adapters/ocrv.py::_candidate_request` 仅从其中 `candidate_payload` 构造实际请求，未映射外层管理字段。A2 补证信封确有 592 字符 `management_summary`、3 项 `management_evidence_refs`，实际 `ocrv-request.json` 没有这些字段。不能把管理动作已提交当成 Checker 已收到补充信息。
- **8000 是另一个入口限制，不是模型上下文结论。** 原生 stderr 为 `background content is 107505 characters, exceeding the hard limit of 8000 (aborting)`；实际版本的 [background loader](https://github.com/alibaba/open-code-review/blob/182898c/cmd/opencodereview/background_file.go) 在调用模型前清洗并计数、超过上限直接拒绝。background 是注入原生组会话的背景，不是原件读取接口；不能用更大模型或把完整报告反复塞入此入口解决读取缺口。现场完整包长度与原生计数不是同一测量。
- **准备检查为什么漏过：** `run_readiness.py::_normal_payload` / `OcrvAdapter._candidate_request` 检查宿主文件存在、字段完整；通讯演练检查投递、native start 与 TOKEN。没有验证接收 Checker 的实际工具能读取 Git 树外原件。通过的是发送与存在性，不是材料可消费性。

最小纠正层在现有 OCRV 适配器：保留固定提交的代码读取，接通仅限本次原始证据的只读入口，并映射已有管理补证。先验证接收者真能读，再谈只传位置；不加通用 shell、存储服务或第二条投递链，不把摘要充当全文。隔离候选实现情况见下文。

### 二、交接：SLK 工程决定与 OCRV 原生生命周期相互独立

- **SLK 已结束责任，OCRV 并不知道。** `slk_checker_decision.py::respond` 调用 RoleHost 提交 whole-CELL 决定并路由下一成员，返回的却只是普通 MCP 文本结果。实际 OCRV [loop.go](https://github.com/alibaba/open-code-review/blob/182898c/internal/llmloop/loop.go) 仅对内建 `task_done` 返回完成；普通 MCP 执行后返回 `tool.Of(result)` 并继续会话。[agent.go](https://github.com/alibaba/open-code-review/blob/182898c/internal/agent/agent.go) 另有逐组调度，单组完成也不等于整次 review 结束。隔离测试确认 SLK 决定接口返回后仍能处理下一 RPC；源码中不存在 D1 提交到原 review 收尾/取消的绑定。幂等拒绝重复决定只防止重复记账，不阻止重复工作。
- **现场与此机制一致。** A1 PASS 后下一 Worker 02:27:13 启动，旧 OCRV 02:35:32 还尝试再次决定；A2 也在下一 Worker 启动后继续旧调用。Supervisor 按精确旧候选/PID/创建时间收起旧调用，不能将这类非自然退出当作推翻已接受 D1 的依据。只再加“不要重复”的提示，或者仅串行组并发，都没有修复生命周期连接。
- **Desktop 是另一处两阶段缺口，不等同于丢消息。** `b208ab4c` 原发送19:04:56Z受理，19:05:57Z因60秒内缺少精确读回证明而失败；19:07:44Z由现有 consumer 确认同一 active turn 的准确消息，再沿同一 operation `54865833` 提交 T126。没有重发。隔离已有用例复现“受理未证明→稍后消费原消息→保留失败历史”，并拒绝重复匹配。现有发送入口超时后退出，没有自行消费后来证明；此 gap 需要人工使用已有恢复入口。
- **不夸大已定位范围。** 后来读回文本4637字符、未截断、新 item 属于原 active turn；没有证据支持本例由大消息截断造成。原轮询响应没有留存，故仍不能确认最初60秒是平台暂不可见、读取视图延迟还是匹配问题；读回文件生成时间不能当成消息实际到达时间。

最小纠正层：让原生调用明确识别本次 whole-CELL 决定后的收尾边界，保留报告，不强杀整 Agent/Session 或合法新调用；Desktop 沿既有同消息/operation 消费入口闭合迟到读回。不能用重发、换 Session、取消身份校验或新恢复器掩盖原失败。

### 三、OW：活动采集语义、证据生命周期与核验覆盖均有缺口

- **本链消费的不是一分钟真实采样。** 已部署 DSH 活动插件与仓内 SHA 完全一致，只在 `agent/status` / `session/event` 更新；长 Shell 未返回就可能无新事件。已部署 OCRV 适配器也与仓内 SHA 一致，创建包装进程就自分配 UUID 并写 RUNNING，其后靠 stderr 每行更新；PID 默认是 PowerShell 包装进程，UUID 不是实际 Go session ID。包装器存活、任意 stderr 或刚生成回执，都不能单独证明模型已工作或当前工具仍在推进。
- **采集与时效契约不匹配，已复现。** `native_activity.py` 默认把最后事件超过300秒判为 `UNKNOWN/NATIVE_ACTIVITY_STALE`，并清空 last_event/waiting_on；OW 每600秒巡查。隔离测试保持 PID/创建时间匹配且存活，仅把检查时间从4分59秒改为6分钟，即从 ACTIVE 变 UNKNOWN。这不是证明停工；已无新事件不等于刚完成一次真实采样。不能单纯刷新时间戳或调大阈值来伪造活动。
- **长编译现场支持这一盲区。** B 原活动序号约八分钟不变，而精确任务的 cargo/rustc/link 子进程 CPU 继续增长；OW 03:37:18 保留 UNKNOWN 并实际报告，Supervisor 核对后等待，03:40:29 原 Shell EXIT0。此次 OW 上报合理，不是产品 FAIL；任何其他 Run 的 CPU 活动不能用来证明本 Run 正常。
- **可变文件不能用作永久证据，已复现。** `_verify_cycle` 与 Rust 写入口重算证据 SHA，引用持续更新的 native-activity 后一有新事件就可能拒绝。隔离 recovery 目录中的文件在未改内容时通过核验、只改内容后被拒，说明该路径并非一概禁止。应保存真实采样的不可变小收据，保留原件身份，而不是删除 SHA 校验；当前统一错误还隐藏了具体是时间、范围还是哈希不符。
- **恢复目录选择不完整，已复现；现场原拒绝仍未完全还原。** `_current_native_start` 只识别 `review-segments/segment-*`，不会从 canonical receipt 自动选中 `recovery/supervisor-input-continuation-*` 的新调用。隔离对照已证实此差异。但原失败轮的部分请求后来被覆盖，不能把现场所有 scope 拒绝都归因于这一选择器，也未发现全局“禁止 recovery 子目录”的规则。
- **防假巡查覆盖不对称，属于新发现的机制风险。** Python `_verify_cycle` 仅在 Worker 持 TOKEN 时重新核对原生事实；Checker 持 TOKEN 时，在范围/时间/哈希检查后返回。隔离伪造 Checker ACTIVE 文件（正确哈希、不存在的任务）被该 Python 核验层接受，native 查询未被调用；Rust 对应专项核验也仅覆盖 Worker。哈希证明文件未改，不证明文件描述真实。未向真实数据库写入，也没有据此认定现场 OW 造假。
- **操作错误仍单列。** cycle211 的 start=end 被正确拒绝，不能归咎探针；临时 PowerShell 数组合并、误用恢复命令、手工 UTF-8 环境也是独立操作错误。正常 UNKNOWN、工具拒绝与伪造事实是不同问题。

最小纠正层：沿现有采集/inspect/admin 链统一“最后事件”与“本次真实采样”的含义，绑定实际任务/原生身份、恢复后的准确入口，并使用不可变收据；补齐 Checker 的事实核验而不是新增监督角色。先去掉错误等价关系，再确定必要的最小字段/代码；不扩成全日志平台，也不把100M日志塞给 OW。
