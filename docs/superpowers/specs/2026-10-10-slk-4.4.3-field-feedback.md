## 三组问题，而不是重复累计缺陷数

### 一、证据没有真正进入 Checker：已有直接证据，优先处理

- **原件不可读。** A1/A2 原始 `checker-decision.json` 均明确说明：索引中的 D0 位于 `.codex/.tmp`，OCRV 的 `file_read` 按 `git show <commit>:<path>` 读取，结果 not found / Filename too long，`file_find` 也找不到。文件存在、路径投递成功，不代表接收 Agent 的工具能够读取；这正是两次 INCOMPLETE 的共同缺口。
- **补充说明被适配时丢掉。** `role_host.py` 把管理说明和原件位置写入 `D1_MANAGEMENT_RETURN` 外层；`adapters/ocrv.py::_candidate_request` 仅从其中 `candidate_payload` 构造实际请求，未映射外层管理字段。A2 补证信封确有 592 字符 `management_summary`、3 项 `management_evidence_refs`，实际 `ocrv-request.json` 没有这些字段。不能把管理动作已提交当成 Checker 已收到补充信息。
- **整份塞入 background 也行不通。** 原生 stderr 明确为 `background content is 107505 characters, exceeding the hard limit of 8000 (aborting)`。这是本次实际 CLI 拒绝，不是仅看到 SLK capacity 默认值就推断的限制；Supervisor 所述完整包长度与该次原生计数不同，不混作同一个测量。该错误本身不证明模型上下文不足，也不意味着直接放大上限就是正确修复。

最小方向：先核对 OCRV 原有读取能力，修正现有材料入口与管理回复的实际请求映射；保留原件、完整准则及关键错误，不能仅重复同一不可读指针、截断原件或把摘要当验收证据。不新增存储服务、协议层或第二条投递链。具体实现须用真实读取工具验证后再定。

### 二、已决定、已投递与已交接不一致：有现场证据，根因待复现

- **旧调用未结束。** Supervisor 反馈 A1/A2 已提交 whole-CELL 决定且触发后续交接，旧 OCRV 调用仍进入下一个原生文件组，甚至再次尝试 `slk_checker_decide`；Supervisor 按原候选、PID 与创建时间核对后，仅结束旧调用并保留非自然退出记录。已有 background 指引已禁止按文件组重复决定，不能把再加一句相同提示当成解决，也不能据旧调用的非零退出推翻已接受 D1。
- **可见消息不等于 TOKEN 已提交。** A2 Checker→Supervisor 的 `b208ab4c` 消息可见，但原 v2 readback / TOKEN 交接未完成；现场使用已有 `consume-desktop-readback` 与 `continue-staged-handoff`、同一 operation `54865833` 才推进。只读检查时结果已为 `OWNED_HANDOFF_COMMITTED`，这证明恢复后的状态，不证明原链一次成功。原始失败原因仍须按原发送/读回记录复现。

最小方向：分别检查原生决定后的调用收尾和现有读回消费边界；保留同一候选、消息、operation 与原始历史，不用重发、重建角色或新恢复器掩盖原失败。不得把“Root 已看到文字”记录成 TOKEN 已交接。

- **待复现的取证问题：** Supervisor 反馈 recovery 子目录原件曾被范围检查拒绝，持续更新的 `native-activity.json` 被当成永久 SHA 证据后导致巡查拒绝。当前源码确实会重新校验引用哈希；仍需核对具体失败记录和合法目录/快照约定，不能直接取消身份、时效和证据完整性校验。
