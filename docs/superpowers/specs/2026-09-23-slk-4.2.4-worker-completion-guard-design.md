# SLK 4.2.4 Worker Completion Guard Design

## Problem

SLK 4.2.3 proves native Worker start and atomically gives the TOKEN to that Worker, but the DSH adapter stops after validating `slk.worker-result/v1`. The source shell may have no role credential, and the immutable Worker task does not carry the current Checker endpoint. Therefore a terminal DSH result cannot safely be interpreted as Worker-owned D0, candidate submission, Checker activation, or TOKEN transfer. A prompt that says “do not alter central state” exposed the gap, but deleting that sentence would not supply the missing authority or address.

The Overwatcher also accepts a complete cycle whose evidence says the current Worker delivery is terminal while the TOKEN remains with Worker and no D0/candidate/handoff exists. Eight syntactically filled checklist fields do not prove this combination is healthy.

## Minimal 4.2.4 boundary

4.2.4 does not make transport a scheduler and does not let Supervisor, Checker, or Overwatcher impersonate Worker. It adds one recoverable Worker-owned continuation and one read-only completion inspection:

1. `continue-worker` is never launched directly by Supervisor or Overwatcher. `slk-transport resume-worker-continuation` resumes the exact DSH `instance_id` + `session_id` proven by the original `started.json`, writes a second native-start receipt, and gives that same DSH Session one immutable continuation task. Inside that resumed Worker process, a headless credential broker decrypts the pre-provisioned Worker DPAPI credential without printing it, places it only in the child `SLK_ROLE_CREDENTIAL`, and invokes `continue-worker`. The caller may wake the same Worker but cannot submit Worker facts itself.
2. The continuation writes deterministic Worker-owned `WORK_STARTED`, `D0_COMPLETED`, and `CANDIDATE_SUBMITTED` facts through `slk-state`, builds the smallest `CANDIDATE_READY` from the immutable Worker result plus frozen CELL goal/D1 criteria, activates the native OCRV endpoint, and reuses `commit-delivery-start` only after a matching `started.json` exists. Request files and IDs are stable, so an exact retry resumes rather than duplicating work.
3. `slk-state write` permits an exact idempotent replay only for effective 4.2.4 Runs. A conflicting reuse of an event ID remains rejected. The atomic delivery-start receipt remains the only TOKEN transition.
4. `slk-transport inspect-worker-completion` is read-only. It combines the immutable transport attempt with a fresh `slk-bi-query run` projection and a supplied observation time/cadence. The source message must bind exactly one positive `TRANSPORT_STARTED` attempt; missing or ambiguous attempt evidence fails closed, and the derived attempt is carried in the inspection and continuation. It distinguishes native work still running, terminal completion inside one cadence, a completed delivery already handed off, D1 states, and a terminal Worker result that still lacks D0/candidate/handoff after one full cadence. The terminal evidence timestamp prevents a historical completion from receiving a fresh grace period. A prior matching observation suppresses only another notification; every cycle stays anomalous until the handoff is repaired.
5. For an effective 4.2.4 Run whose TOKEN is held by Worker, each Overwatcher cycle must include the hashed inspection output. A `WORKER_COMPLETION_HANDOFF_MISSING` result cannot be recorded as CLEAR; the cycle must carry the dedicated anomaly and the Overwatcher records/notifies Supervisor once. The Overwatcher still cannot write engineering facts or move TOKEN.

## Capability preflight

Before dispatch, Checker verifies that the Worker continuation has: the exact active Checker endpoint, an exact resumable DSH Session, executable state/query/transport commands, a decryptable DPAPI credential bound to the same active Worker role, and writable immutable evidence roots. The preflight authenticates the credential through a non-mutating role check and emits only the role instance match, never the secret. Failure is `WORKER_CONTINUATION_NOT_READY`; no CELL delivery starts. Secrets never enter endpoint, envelope, result, task, prompt, log, or evidence files.

The current R3B T014 has an exact DSH session in `started.json` and a dedicated encrypted `worker-flash.dpapi` file; their presence has been checked without decrypting or printing the credential. Recovery remains conditional on a non-mutating credential/role match, explicit 4.2.4 adoption, and resuming that exact Session with the registered Checker endpoint. If the credential cannot authenticate as `SLK-RC08-R3B-WORKER-02`, recovery is blocked rather than performed by Supervisor. The existing candidate/result and TOKEN remain unchanged until that role-owned continuation succeeds. This maintenance candidate does not perform that recovery.

## Non-goals

No new role, Run, resident service, heartbeat, daemon, BoM route, model change, D1 decision, writable BI, product edit, or automatic inference from process exit is introduced. Existing 4.2.3 Runs retain 4.2.3 behavior until explicit adoption.
