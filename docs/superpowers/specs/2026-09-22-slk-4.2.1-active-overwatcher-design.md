# SLK 4.2.1 Active Overwatcher Design

Date: 2026-09-22
Status: Approved for implementation

## Problem

The unpublished 4.2.0 candidate described the optional Overwatcher as an event-woken observer that ended its turn after each check. That wording cannot satisfy the Owner requirement that the selected Overwatcher Agent Session remain actively running for the whole Run and inspect operation without waiting for another role to wake it. The candidate is therefore withdrawn and must not be enabled.

## Decision

SLK 4.2.1 keeps the 4.2 topology and authority boundaries, but replaces the defective observation semantics. A Run may still have zero or one dedicated, non-reusable Overwatcher Agent Session. When one is bound, that same Session holds one foreground active observation turn until Run termination. It performs complete observation cycles at a Supervisor-and-Owner-confirmed interval from 180 through 300 seconds; 240 seconds is the recommended default. Incoming events may cause an earlier cycle but never replace the proactive cycle.

This is not a heartbeat or scheduled task. SLK must not create a Codex automation, heartbeat, cron job, Windows Scheduled Task, daemon, service, detached helper, hidden/background Agent, or second observer. The interval is held inside the already-active Overwatcher turn. A runtime unable to keep that Agent Session and its foreground turn active fails readiness closed.

## Cycle contract

Every cycle records one compact, append-only fact bound to the current Run, Overwatcher identity, Session, plan revision, and monotonic cycle number. It includes the cycle start/completion time, next inspection time, current GO/CELL/attempt, TOKEN holder and sequence, latest authoritative event and message references, native active-turn evidence, a closed checklist result, evidence references, and any anomaly codes. It never copies full logs or claims engineering acceptance.

The fixed checklist observes:

1. current Run, plan revision, GO/CELL/attempt, TOKEN position, and latest accepted event;
2. frozen Supervisor, Checker, Worker, and Overwatcher identities, Sessions, endpoints, and native execution evidence;
3. outstanding direct handoffs and their sent, delivered, received, or started evidence;
4. CELL lifecycle through dispatch, execution, D0, D1, rework, and closure without treating delivery as acceptance;
5. unexplained stalls, duplicate dispatch/check/rework, endpoint drift, duplicate Run identity, or stale activity claims;
6. read-only BI projection consistency with authoritative state;
7. this Overwatcher Session, foreground turn, cadence, and non-overlapping cycle health;
8. terminal Run closure and Overwatcher archive duty.

## Authority and reporting

Overwatcher may update only its own cycle status and append operational observations. It cannot write TOKEN, CELL, D0/D1/D2, acceptance, plan, role replacement, product files, or BI. BI derives a read-only latest-cycle summary from accepted state.

Normal cycles create no user-visible status message. An anomaly report names the exact Run/GO/CELL/attempt, anomaly code, last trusted state, missing or conflicting evidence, any exact retry already attempted, and the responsible role. It may replay one unchanged message under the existing communication-recovery contract or wake Supervisor. It never changes meaning, chooses an engineering route, or replaces a role.

## Liveness and closure

Binding requires the chosen interval, a foreground-turn capability declaration, and native active-session evidence. A cycle must be monotonic and must complete before the next cycle starts. A missing or invalid cycle is not repaired by a free-text claim, visible task, old running state, heartbeat, or scheduled wake.

One overdue cycle produces `OVERWATCHER_ACTIVE_DEGRADED` and an immediate self-check. Two consecutive overdue cycles, a closed turn, or a missing foreground-turn proof produces `OVERWATCHER_INACTIVE`; no new dispatch or handoff may begin until Supervisor resolves the binding. Work already executing is not forcibly interrupted. Runs with no Overwatcher retain the original Supervisor/Checker/Worker route.

After authoritative Run termination the Overwatcher records closure, stops its foreground turn, and archives the same Session. The Session is never reused by a later Run.

## Compatibility

4.2.0 was never tagged or released. Local 4.2.0 installations are semantically defective and must not start a new Run. Existing state is migrated atomically to 4.2.1; an old Overwatcher binding does not gain active status by reinterpretation and must be rebound or closed through the versioned migration procedure. 4.1.1 Runs without an Overwatcher retain their original compatibility path.
