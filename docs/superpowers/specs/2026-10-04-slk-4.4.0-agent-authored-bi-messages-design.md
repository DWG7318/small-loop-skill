# SLK 4.4.0 Agent-authored BI Messages Design

- Date: 2026-10-04 (Asia/Shanghai)
- Status: proposed implementation contract
- Baseline: SLK 4.3.6 at `1a2a7b1695c4917dd9a1685411a8082e4122274d`
- Target: SLK 4.4.0; LE BI / WebBI 1.1

## 1. Decision

SLK 4.4.0 extends the existing authoritative state path instead of adding a second notification truth:

`Agent -> slk-state-core validation -> authoritative typed record -> BI/WebBI projection -> optional ntfy delivery`

The originating Agent selects a predeclared machine type when it records a fact. The state core validates the type, authoring role, Run scope, identity, and payload. BI and WebBI are read-only consumers. They may store presentation-only read and delivery cursors, but they must not classify, reinterpret, or rewrite engineering facts.

This is a BI foundation change, not a new role, new SLK gate, or parallel workflow engine.

## 2. Authoritative typed-message contract

### 2.1 Reuse existing facts

The message catalog is built from existing role-authored `EventType` values and existing Overwatcher typed observations/incidents. A visible update points to one immutable source record; it does not copy free text into a second semantic record.

Each eligible source record provides at least:

- `message_id`: stable globally unique record identity;
- `run_id`: exact SLK Run identity;
- `source_kind`: event, Overwatcher observation, or Overwatcher incident;
- `message_type`: exact closed catalog identifier;
- `author_role`: source Agent's registered SLK role;
- `author_identity_ref`: current versioned team-registry identity;
- `scope`: applicable Run/GO/CELL/Round reference;
- `occurred_at`: source occurrence time;
- `summary` and `evidence_refs`: bounded content already permitted by the source contract;
- `source_revision`: monotonic source ordering token where available.

The catalog adds display metadata only: stable identifier, Chinese label, allowed source kind, allowed author role, severity/display group, and whether it is eligible for notification selection. That metadata is not a new Run fact.

### 2.2 Fail-closed authoring

The state core rejects:

- unknown or free-text message types;
- a known type authored by a role that does not own it;
- missing Run, author identity, unique record identity, or required scope;
- a BI/WebBI process attempting to author an engineering message;
- the same `message_id` with different content;
- an Overwatcher observation presented as a technical D0/D1/D2 event;
- any type inferred after the fact from display text, elapsed time, color, or projection state.

Existing state records remain the engineering authority. No migration may silently reinterpret an untyped legacy projection as a typed message.

## 3. Green-dot semantics

A green dot means: **this UI has at least one unread eligible authoritative typed record for this Run**.

- It does not mean that the Run is healthy, complete, accepted, or progressing.
- Local polling, a duration counter, screen refresh, projection rebuild, normal no-change OW inspection, and repeated upload of the same `message_id` do not create a green dot.
- Opening the Run marks only the currently displayed message revision/set as read on that client.
- A later message gets a new green dot. An older snapshot cannot overwrite a newer read cursor.
- Desktop BI and WebBI keep separate local read cursors. Read state is UI metadata and never feeds SLK authority.
- Historical bootstrap establishes the initial read baseline and does not flood WebBI or ntfy with old messages.

## 4. Desktop BI and WebBI data path

### 4.1 Desktop BI

Desktop BI keeps its current local read-only projection and three-second visible-window refresh. It shows the computer name in its header and a compact green dot beside each Run with unread messages.

Desktop BI may upload a bounded projection envelope to WebBI. The envelope contains no information beyond what desktop BI is already allowed to display, plus source identities needed for deduplication and the device label/ID already approved for display.

### 4.2 Upload

- The existing BI process performs the upload; no Node sidecar, extra Agent, or per-Run sync component is introduced.
- Upload is incremental, idempotent by `message_id`/revision, and attempted every 30 seconds when new data exists.
- Devices upload independently. Runs from different devices do not synchronize with or overwrite one another.
- Offline failure preserves local BI operation and retries the pending bounded envelope later.
- A Run's WebBI space persists; completion or abandonment changes it to archived rather than deleting it.
- Server identity keys include the stable device ID and Run ID so same-named Runs on different computers cannot collide.

### 4.3 WebBI

WebBI is a browser UI over the persisted upload store. Its default list is `进行中`; `已归档` remains available. The list opens a Run detail page; it does not add a per-computer top-level mode or an `全部` mode.

While open, WebBI refreshes its backend view every 30 seconds. This browser refresh is not the device upload mechanism and does not generate messages.

WebBI uses BI 1.1 styling and responsive browser layouts. It may be visually refined, but it must remain factual, calm, accessible, and no more semantically powerful than desktop BI.

## 5. ntfy delivery

WebBI owns an optional mobile-notification settings page with:

- private ntfy server URL;
- topic;
- token, or username/password;
- test-message action;
- mode: all eligible new message types, or an explicit subset of catalog types.

Rules:

- The checkbox list is generated from the exact shared message catalog. WebBI cannot invent broad categories and map records into them.
- Only a newly ingested authoritative typed record may enqueue a notification.
- The WebBI backend, not the browser, sends ntfy. Secrets remain server-side and are write-only/masked in browser responses and logs.
- A delivery ledger keyed by destination configuration version and `message_id` prevents duplicate sends.
- Read/unread state and ntfy delivered/not-delivered state are separate.
- Configuration changes do not replay historical messages unless a future explicit Owner-approved replay feature is designed.
- Notification failure records operational delivery status without changing the SLK source fact or fabricating a new engineering event.

## 6. Boundaries

This change does not:

- let BI/WebBI write SLK Run facts, TOKEN, D0/D1/D2, role bindings, or OW conclusions;
- infer truth from text, window state, elapsed time, or a green dot;
- expand WebBI beyond the desktop BI data envelope;
- add a new runtime role, message bus, Node service, MCP server, or Agent;
- replace Temporal, role-to-role transport, or the team registry;
- make ntfy part of authoritative role communication;
- expose credentials, raw private logs, or unrestricted evidence payloads to the web.

## 7. Minimal implementation surface

1. State core: expose/validate the closed shared message catalog and source-record identity rules.
2. BI contracts/projection: consume authoritative message identities, maintain local read cursors, and add device/BI version fields.
3. BI uploader: bounded 30-second incremental envelope with idempotent retry and no extra process.
4. WebBI store/API/UI: persistent per-device Run archive, responsive list/detail, local read cursors, and 30-second browser refresh.
5. ntfy settings/delivery: server-side encrypted/secret storage appropriate to the selected Cloudflare deployment, exact-type filters, test action, and idempotent delivery ledger.
6. Documentation/tests/manifests: update only coupled artifacts and keep root/install mirrors byte-consistent where required.

## 8. Acceptance tests

### State and authority

- Every existing technical event type is accepted only from its owning role.
- OW observation/incident types remain OW-owned and cannot claim D0/D1/D2 authority.
- Unknown/free-text type, wrong role, missing identity/scope, or BI-authored fact fails closed in normal and optimized Python/runtime validation paths where applicable.
- Same ID/same content is idempotent; same ID/different content is rejected.

### Green dots

- One new eligible source record creates one unread marker.
- Three-second refresh, 30-second refresh/upload, elapsed-time changes, duplicate record, and normal no-change OW inspection create none.
- Opening one Run clears only the displayed revision for that client; a later record restores its dot.
- Bootstrap history is silent and an old snapshot cannot regress the read cursor.

### Multi-device WebBI

- Two devices upload independently and same-named Runs remain isolated by device ID plus Run ID.
- Upload loss/offline recovery does not block local BI and retry does not duplicate records.
- Active and archived spaces persist; no terminal Run is deleted.
- WebBI exposes no field absent from the approved desktop BI envelope except display-only device attribution and UI metadata.

### ntfy

- `all` and selected-type modes use exact catalog IDs.
- Unselected, duplicate, historical-bootstrap, untyped, or invalid-role records send nothing.
- Test message is explicitly labeled as configuration test and is not inserted as a Run fact.
- Browser/API responses and logs never expose stored secret values.
- Notification failure does not mutate the authoritative source record and can be retried idempotently.

### Compatibility and UI

- Existing BI remains usable when WebBI or network is unavailable.
- Existing SLK state and method semantics remain unchanged.
- Desktop BI remains compact; WebBI works at phone, tablet, and desktop widths with keyboard/focus and reduced-motion support.

## 9. Rollout

Implementation starts with failing contract tests, then state-core validation, desktop BI projection/upload, WebBI persistence/UI, and finally ntfy. WebBI/ntfy stays non-authoritative throughout. Publication, Cloudflare production deployment, credentials, and remote release remain separate Owner-authorized gates.
