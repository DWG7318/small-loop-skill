# SLK 4.0 State, BI, and Agent Read Interface Design

## 1. Purpose

SLK 3.0.8 defines a lightweight linear Loop Engineering method, but its state is still primarily carried by visible handoff messages and a Markdown Run record. That is sufficient for one team to work, yet it is not sufficient for several SLK Runs operating concurrently, for reliable cross-Agent reading, or for a future LCaS + MiniMax Overwatcher to compare recorded progress with the three members' real reports.

SLK 4.0 will add a durable state and presentation layer without changing the engineering method. It will preserve the Supervisor, Checker, and Worker roles; the Run, GO, and CELL hierarchy; D0, D1, and D2 ownership; rework; exemptions; the linear `SLK TOKEN`; and the existing communication relationships.

The new layer has three purposes:

1. preserve complete SLK state and evidence outside the product repository;
2. present all local SLK Runs in one read-only BI application; and
3. expose a stable read-only interface for other Agents and a future LCaS Overwatcher.

## 2. Canonical boundaries

The following boundaries are normative:

- The Supervisor, Checker, and Worker are the only SLK roles that may author Run data.
- A new SLK Run creates a new Supervisor, Checker, and Worker. Role instances are not reused across Runs.
- BI does not verify, infer, repair, dispatch, wake, approve, or modify work. BI only displays recorded facts.
- Owner can view the BI and direct the project through the normal SLK relationship, but has no BI or Agent Read API write path.
- Other Agents can read through the Agent Read API and cannot write SLK state.
- The future Overwatcher is an active external supervisor of truth, not a fourth construction role. It may read, contact the three members, compare answers with records and evidence, and report discrepancies. It cannot edit BI data, hold the `SLK TOKEN`, perform D0/D1/D2, or replace a member's authorship.
- This design does not add Patrol, peer-state watching, `wait_threads`, an acknowledgement round, a fourth SLK role, or a background state-management service.

## 3. Architecture

The first implementation is a standalone Windows desktop application that can later become a native LCaS panel without being rewritten.

```text
SLK Run A: Supervisor A / Checker A / Worker A
SLK Run B: Supervisor B / Checker B / Worker B
SLK Run C: Supervisor C / Checker C / Worker C
                         |
                         v
                 central slk.db
                  /           \
                 v             v
        read-only SLK BI   Agent Read API
```

The implementation stack matches the current LCaS GUI:

- Tauri 2 desktop shell;
- Rust backend and reusable core;
- `rusqlite` with bundled SQLite;
- React 19 and TypeScript frontend;
- Vite build system;
- Tailwind CSS 4 styling; and
- Vitest frontend tests.

The Rust state/query functionality and React feature UI must not depend on standalone-window assumptions. The standalone Tauri shell is an initial host. A future LCaS release can link the Rust core and mount the React feature module directly rather than use an iframe or start a second BI service.

The standalone BI and its query tools are installed once per computer. They are not copied into, rebuilt for, or redeployed by each project or Run.

## 4. Central data root

The first deployment selects one machine-wide `SLK_DATA_ROOT`. A small configuration file at `%LOCALAPPDATA%\SLK\config.json` stores only the selected root path. The root contains the authoritative database, durable evidence, exports, and backups.

```text
<SLK_DATA_ROOT>\
  slk.db
  evidence\
    <PROJECT-ID>\
      <RUN-ID>\
  exports\
    <PROJECT-ID>\
      <RUN-ID>\
        SLK-RUN-<RUN-ID>.md
  backups\
```

Project repositories do not contain SLK runtime records. A stable `PROJECT-ID` is independent of the project's current filesystem path. Project path, repository identity, and last-seen facts are metadata, so deleting or moving a project does not delete its SLK history.

Records and evidence are retained indefinitely by default. There is no automatic cleanup. If Owner later requests archival or cleanup, an authorized Supervisor performs and records the action; Owner does not directly edit BI data.

Moving the central root uses copy, verification, and one final configuration switch. Two roots must not be treated as simultaneously authoritative.

## 5. Engineering hierarchy

The state model preserves the full SLK hierarchy:

```text
Project
  Run
    GO-001
      CELL-001
      CELL-002
    GO-002
      CELL-003
```

One SLK owns one Run. GO and CELL remain on one linear execution path. Every state-bearing record includes the applicable `project_id`, `run_id`, `go_id`, `cell_id`, attempt or rework number, plan revision, and role instance.

BI presents this hierarchy at three levels:

1. a machine-wide list of active and archived Runs;
2. the ordered GO progress inside one Run; and
3. the CELL, D0, D1, rework, evidence, and handoff history inside one GO.

## 6. Logical data model

The initial database uses a small set of explicit concepts rather than a general workflow engine:

- `projects`: stable project identity, names, repository facts, and last-known path;
- `runs`: Run goal, boundaries, current state, current plan revision, and closure state;
- `go_nodes`: ordered GO definitions and outcomes;
- `cell_nodes`: ordered CELL definitions, attempts, and outcomes;
- `plan_revisions`: immutable snapshots of the initial plan and subsequent engineering-plan changes;
- `role_instances`: role, Agent runtime, provider, model, reasoning setting, session identity, lifecycle, predecessor, and successor;
- `role_credentials`: hashed, Run-scoped write capabilities for the current role instances;
- `token_events`: monotonically ordered `SLK TOKEN` handoffs and responsibility boundaries;
- `work_events`: append-only construction, D0, D1, rework, exemption, D2, correction, and closure facts; and
- `evidence`: evidence identity, path, hash, type, producing role, and related engineering node.

Large logs, screenshots, reports, and other evidence remain files under `SLK_DATA_ROOT`. SQLite stores their identities and hashes, not their binary contents.

## 7. Role identity and replacement

Every role instance records at least:

- Run and role;
- Agent runtime, such as Codex, DSH, OCRV, or a future Agent;
- provider and model name;
- reasoning level or equivalent setting;
- session or thread ID;
- creation, takeover, exit, and replacement times;
- predecessor and successor role instance IDs; and
- current or historical CELL responsibility.

Secrets, API keys, provider tokens, and raw write credentials are never written to BI-readable records.

If a role changes model or session, the old identity is not overwritten. `MODEL_CHANGED` records old and new model configuration, reason, and CELL scope. `SESSION_REBOUND` records old and new session identity and the recovery boundary. A model escalation scoped to one CELL does not silently change the next CELL's baseline.

Role replacement does not create a new Run. The stable Supervisor, Checker, or Worker position receives a new `role_instance_id`; the old credential is revoked; a new credential is issued; and a `ROLE_REPLACED` event records the reason and takeover point. All earlier records retain their original author attribution.

BI shows both the three current role instances and their complete replacement history.

## 8. Agent addressing and direct transport

Supervisor, Checker, and Worker are three independently running Agents, not three labels inside one conversation. Recording a session ID is therefore necessary but insufficient. SLK 4.0 must provide exact addressing and real activation across the three Agent runtimes.

Each active role endpoint records:

- `run_id` and `role_instance_id`;
- Agent runtime and transport adapter;
- host identity;
- thread, session, or instance ID;
- endpoint version and replacement state; and
- the minimum native address required to start the target Agent without relying on a conversation title.

The required direct communication graph remains:

```text
Supervisor Agent -> Checker Agent
Checker Agent -> Worker Agent
Worker Agent -> Checker Agent
Checker Agent -> Supervisor Agent
```

Each sender uses the receiver's current endpoint and native runtime interface. The transport implementation is a library and a set of runtime adapters used by the three Agents; it is not a fourth Agent, state authority, message-approval role, or resident relay service.

The initial runtime bindings are:

- Codex Supervisor: exact Codex thread ID plus host identity; an external connector resumes the saved thread and starts a real turn through the official Codex SDK or App Server thread APIs.
- OCRV Checker: exact Run, CELL, review invocation, and OCRV session identity; a Checker harness invokes the existing OCRV/Qwen review path and owns the Checker's outgoing handoff.
- DSH Worker: stable Run-scoped instance ID plus DSH session identity; a Worker harness starts or resumes the correct DeepSeek Harness session.

The official Codex SDK supports resuming a thread by ID and running another prompt, and Codex App Server exposes `thread/resume` followed by turn execution. DSH already exposes stable per-instance homes and session resume. OCRV already emits per-Run/CELL review identities and session IDs. These are sufficient integration primitives, but the current local DSH and OCRV wrappers do not yet constitute an accepted end-to-end transport.

Every transport attempt carries a closed envelope containing message ID, token sequence, Run, GO, CELL, sender role instance, receiver role instance, endpoint version, payload type, payload hash, and the actual SLK payload or its durable location. It contains no provider secret or role credential.

A database write or background text insertion is not delivery. Delivery succeeds only when the target's native runtime call accepts the exact endpoint and starts the target turn or job. After success, the sender records the handoff. On explicit transport failure, the sender retains the current token and the failed attempt is recorded without advancing responsibility. The receiver does not send an acknowledgement-only turn; it writes `WORK_STARTED` as the first act of the real assigned work.

Session recovery appends `SESSION_REBOUND`, creates a new endpoint version, and retires the previous endpoint. Handoffs addressed to a retired endpoint are rejected. Different Runs cannot share one role endpoint.

Before dependent BI/state integration is accepted, a no-project-change transport drill must prove the full four-leg graph, session recovery, explicit failed-delivery behavior, and two simultaneous SLK Runs without cross-Run delivery. Existing BoM task-pack and Codex CLI patterns may inform implementation, but they are not accepted as proof of Codex Desktop thread activation.

## 9. Authorship and permissions

Each role writes directly through the shared Rust/CLI database interface. That interface is a safe SQLite access boundary, not a new role, relay, message router, or approval layer.

The role scopes are:

- Supervisor authors Run creation, imported approved plan, role identity, Run/GO-level plan changes, exceptions and exemptions, D2, role replacement, closure, and archive state.
- Checker authors CELL dispatch, pre-dispatch calibration, a same-goal local split of one CELL into two serial CELLs, D1, focused rework requirements, and handoff to Supervisor.
- Worker authors work start, factual progress, blockers, actual changes, minimum D0, candidate identity, evidence, and handoff to Checker.

A change that affects the Run, GO, acceptance target, or wider technical route remains a Supervisor decision. The database does not move existing SLK responsibility between roles.

Each Run has separate Supervisor, Checker, and Worker write credentials. An event is accepted only when the current role instance, Run, credential, engineering node, and event type agree. BI and the Agent Read API open the database read-only and possess no write credential.

Run initialization bootstraps the Supervisor role credential. Supervisor registers the Checker instance and Checker registers the Worker instance as part of the existing creation chain. Replacement revokes the prior instance credential and issues a credential only to the new instance. These actions establish database authorship; they do not add another communication or approval round.

Historical events are append-only. Even an authorized role corrects a mistake by appending a correction event that references the original event and explains the correction. The original event remains visible.

## 10. `SLK TOKEN` and displayed activity

The `SLK TOKEN` remains the core communication and responsibility mechanism. It is not reduced to dashboard metadata. Each successful handoff retains the current SLK meaning: a monotonically increasing token sequence, Run, GO/CELL location, node, sender, receiver, candidate when applicable, next action, and record identity.

BI does not decide whether an Agent is working. The three roles write their own factual state:

1. a real handoff records that responsibility was delivered;
2. the receiving role writes `WORK_STARTED` as the first record of its actual work, without sending an acknowledgement-only message;
3. BI displays `working` only while the latest authored state says the role has started and has not completed, failed, blocked, or handed off that node; and
4. completion, failure, blocker, or handoff ends that displayed activity.

The database is the role-authored record, not an independent truth verifier. BI does not inspect processes, poll conversations, infer activity from old messages, or change a state because time passed. A future Overwatcher may independently question the members and compare their answers, but any BI correction is authored by the appropriate Supervisor, Checker, or Worker.

## 11. Engineering-plan revision

The initial Run design contains the Run goal, ordered GO list, ordered CELL list or approved near-term window, acceptance intent, role/model choices, and relevant constraints. It is stored as `plan_revision=1` when the Supervisor initializes the Run record after takeover.

If engineering facts require a different route, Supervisor appends a new plan revision. The revision records:

- the triggering facts and reason;
- affected GO and CELL nodes;
- preserved completed work;
- added, split, merged, cancelled, or replaced future nodes;
- the revised remaining path; and
- unresolved risk or Owner-controlled resource decisions.

Completed CELL history is never rewritten. If a new plan invalidates part of an earlier result, the new plan adds the required rework or new CELL and preserves the earlier result as history. Every subsequent event references the plan revision under which it occurred.

## 12. Markdown and evidence

SQLite is the structured authority for state and event history. `SLK-RUN-<RUN-ID>.md` is an automatically generated, human-readable export, not a second manually maintained authority.

The export includes:

- Run objective and boundaries;
- plan revisions;
- GO/CELL sequence and outcomes;
- role identities, model/session changes, and replacements;
- D0, D1, D2, rework, exemptions, errors, and corrections;
- candidate identities and evidence paths; and
- final result, limitations, and archive state.

Each successful event transaction attempts to refresh the Markdown export. Export failure does not roll back a valid database transaction; the export can be regenerated deterministically from SQLite.

Evidence is copied or produced under the central Run evidence directory and registered with a cryptographic hash. Missing or hash-mismatched evidence is displayed as such. BI never repairs or replaces evidence automatically.

## 13. BI behavior

The BI is a read-only status application. Its first version includes:

- global active-Run overview plus archived and closed history;
- project, Run, role, model, session, GO, CELL, plan revision, and current-token views;
- clear display of role-authored states, including `working` where recorded;
- D0/D1/D2, rework, exemption, error, correction, and evidence timelines;
- role-replacement and model/session-change history;
- search, filter, refresh, evidence viewing, and Markdown export; and
- automatic local refresh plus a manual refresh action.

It does not include write forms, dispatch buttons, wake actions, acceptance controls, exemption controls, plan editors, or repair actions.

## 14. Agent Read API

The install includes an on-demand `slk-bi-query` command that provides a stable read-only JSON interface while the BI window is closed. It opens the configured database for the duration of the query and then exits; it does not require a resident HTTP service. It supports at least:

- listing projects and Runs;
- reading one Run summary;
- reading ordered GO and CELL status;
- reading current token and current role identities;
- reading role model, reasoning, session, replacement, and lifecycle facts;
- reading plan revisions;
- reading D0/D1/D2, rework, exemption, error, and correction summaries; and
- reading evidence metadata and durable paths.

Queries that address a specific Run require an explicit `run_id`. The API never guesses the caller's intended Run. It exposes no write method and no role credential.

The standalone BI and the query interface share `slk-state-core`; they do not implement separate interpretations of the database.

## 15. LCaS and Overwatcher path

The SLK 4.0 repository delivers the reusable boundaries needed for later embedding, but does not modify LCaS or implement MiniMax supervision.

A recommended LCaS rc.08 or rc.09 upgrade can:

1. mount the React SLK BI module as an LCaS panel;
2. link the Rust state/query core or use its stable read contract;
3. let the LCaS + MiniMax Overwatcher read all local SLK Runs;
4. use recorded Agent, model, and session identities to contact Supervisor, Checker, and Worker directly;
5. compare their answers with tokens, state, and evidence; and
6. request that an authorized SLK member correct or supplement inconsistent records.

The Overwatcher may actively communicate and report, but it remains read-only with respect to SLK BI data.

## 16. Concurrency and failure handling

SQLite uses WAL mode, foreign keys, explicit transactions, and a bounded busy timeout. Separate Runs may write concurrently. Within one Run, the single active `SLK TOKEN` keeps legitimate work on one linear responsibility path.

Each state change is one atomic transaction. A failed transaction creates no partial state. A short lock conflict may be retried a bounded number of times; persistent failure is returned to the current role and is not recorded as success.

Schema migration creates a consistent backup first. Migration failure leaves the previous database and configured authority intact. Database read failure is shown directly by BI and the Agent Read API; neither guesses state.

Database unavailability does not modify project source, but a member must restore record writeability before creating additional authoritative SLK state. This prevents undocumented progress while avoiding a new background service dependency.

## 17. Existing-record transition

New SLK 4.0 Runs use the central database from their first Supervisor record. Existing closed Markdown Runs may be explicitly imported as archived historical records with source hashes. They are not silently reinterpreted as live state.

An active pre-4.0 Run is migrated only by its current Supervisor. The Supervisor records the latest valid token, Run/GO/CELL position, plan, role identities, candidate, and evidence boundary as an explicit migration event before continuing. Automatic discovery or silent migration is not allowed.

## 18. Required SLK method updates

The implementation updates only the Skill areas directly affected by the state architecture:

- the main Skill describes central state as the durable record of the existing linear token, not a new role or approval layer;
- `slk-plan-run` preserves Run-to-GO-to-CELL planning and includes plan revision identity;
- `slk-record-run` writes structured events and regenerates Markdown;
- `slk-manage-team` records Agent, model, reasoning, session, credentials, and replacement history;
- dispatch, execute, check, rework, adjust, recovery, and close Skills author their existing facts at their existing boundaries; and
- earlier language stating that the token has no external state system is replaced with the new exact boundary: the database records the token but does not drive, verify, or replace the Loop.

The update does not change role ownership, the communication graph, D0/D1/D2 meaning, model-selection policy, ordinary rework, exemption policy, or the recommendation against Patrol and peer-state watching.

## 19. Verification and acceptance

### Cross-Agent transport

- exact endpoint resolution without title matching;
- Supervisor-to-Checker, Checker-to-Worker, Worker-to-Checker, and Checker-to-Supervisor real activation;
- failed delivery retaining the sender's token;
- retired endpoints rejecting new handoffs;
- session rebound resuming at the recorded boundary; and
- two concurrent SLK Runs completing the transport drill without identity, payload, or endpoint crossover.

Verification covers:

### Rust core and SQLite

- schema creation and migration;
- role-scoped authorization and revoked credentials;
- append-only history and correction links;
- Run, GO, CELL, plan-revision, and token invariants;
- role replacement, model change, and session rebound;
- concurrent writes from multiple independent Runs without cross-Run leakage;
- transaction rollback, lock handling, backup, and recovery;
- deterministic Markdown export; and
- evidence registration and hash mismatch reporting.

### Agent Read API

- exact JSON schema and stable ordering;
- explicit Run selection;
- complete role, plan, token, inspection, and evidence projection;
- operation while the BI window is closed; and
- absence of every write path and credential field.

### React and Tauri BI

- global active and archived Run views;
- Run-to-GO-to-CELL navigation;
- current and historical role identity display;
- correct rendering of authored `working`, delivered, blocked, rework, inspection, exemption, and closed states;
- plan-revision and replacement timelines;
- database/evidence error states;
- refresh, search, filter, viewing, and export behavior; and
- Windows build, install, upgrade, and uninstall behavior without deleting `SLK_DATA_ROOT`.

### SLK method regression

- the three roles and their existing responsibilities remain unchanged;
- one Run retains one linear GO/CELL path and one current token;
- no Patrol, `wait_threads`, peer watching, acknowledgement round, fourth role, or redundant inspection layer is introduced;
- D0, D1, D2, rework, exemption, and model escalation retain their existing semantics; and
- all existing SLK validation remains green after intentional state-record migration.

## 20. Completion criteria

The feature is complete when:

1. the complete Supervisor-to-Checker-to-Worker-to-Checker-to-Supervisor graph has passed real no-project-change activation tests for two concurrent Runs;
2. several independent SLK Runs can register and update concurrently without identity or state crossover;
3. each Run preserves Run, GO, CELL, token, plan, role, model, session, inspection, rework, exemption, correction, and evidence history;
4. BI accurately displays only the facts authored by the three roles and offers no mutation path;
5. another Agent can obtain the same state through the read-only API without opening BI;
6. Markdown records can be regenerated from SQLite;
7. project deletion does not remove central history;
8. the standalone application uses the LCaS-compatible stack and exposes reusable module boundaries; and
9. the future LCaS rc.08/rc.09 Overwatcher can be built against the documented read and identity contracts without changing the SLK database authority model.
