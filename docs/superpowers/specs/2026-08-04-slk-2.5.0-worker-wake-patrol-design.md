# SLK 2.5.0 Worker Wake, Run Patrol, and Layered Progress Design

## Status

Owner-approved design for implementation on
`feature/slk-2.5.0-worker-wake-patrol`. No remote operation is authorized.

## Objective

SLK 2.5.0 adds seven hard rules to one bounded strictly serial Run:

1. a four-level Worker-only wake ladder for the original bound Checker;
2. no long-lived or looped Supervisor `wait_threads`;
3. exactly one visible, non-authoritative Run Patrol and heartbeat;
4. a precise distinction between visible peer tasks and prohibited subagents;
5. layered real-time progress with one reporting owner per layer.
6. device- and cumulative-load-aware CELL capacity planning before dispatch;
7. default-deny task Pin authority for SLK technical roles, with Patrol denied separately.

The change preserves Worker ownership, Control responsibility authority, D0-D3,
strict serial GO execution, candidate binding, causal repair, and LCCoding
boundaries.

## Non-goals

- No generic message bus.
- No D4 or new technical verdict.
- No second Worker or replacement Checker.
- No SLK-owned thread, heartbeat, or automation Runtime.
- No code, plan, test, or acceptance judgment by Patrol.
- No per-CELL forwarding to Supervisor or Owner.
- No general device monitor, scheduler, benchmark daemon, or resource Runtime.
- No Pin-based status board, progress marker, role registry, or recovery index.
- No changes to LCCoding, Calabash, CLK, or GLK.

## Approaches considered

### Documentation only

Rejected: prose cannot mechanically reject wrong roles, guessed thread IDs,
Supervisor waits, duplicate Patrols, stale counters, or skipped wake levels.

### SLK runtime orchestrator

Rejected: direct orchestration would duplicate Codex runtime capabilities and turn
the method into a control platform.

### Versioned contracts, immutable traces, and a pure validator

Selected: the host performs thread/heartbeat operations; SLK defines and validates
preflight, wake, patrol, simulation, and progress evidence. An injected logical
clock proves two-minute limits without real sleep.

## Topology and authority

Formal execution conversations remain:

```text
CONTROL
WORKER
```

Each Run additionally has exactly one visible safeguard conversation:

```text
RUN_PATROL
```

`RUN_PATROL` is not a formal technical role. It owns no D0-D3, planning, routing,
product write, verification, or acceptance authority. The complete visible set is
three conversations, while the formal engineering topology remains Control plus
Worker.

Control still activates exactly one responsibility:

```text
SUPERVISOR_RESPONSIBILITY
CHECKER_RESPONSIBILITY
VERIFIER_RESPONSIBILITY
```

Worker wakes the same Control conversation while it holds
`CHECKER_RESPONSIBILITY`; no replacement Checker is created.

Model bindings:

- method-owner task: `gpt-5.6-sol` with `xhigh`;
- Run Patrol: `gpt-5.6-luna` with `xhigh`.

## Admission and readiness

Before formal Worker dispatch, `RUN_RUNTIME_CONTRACT` binds:

- Run, baseline, Required-set versions, and hashes;
- one Control, one Worker, one Patrol conversation;
- original Checker `thread_id + host_id`;
- exactly one Patrol heartbeat;
- Patrol model and 10, 15, or 30 minute interval;
- Worker capabilities for send, read, list, unarchive, bounded ACK wait,
  temporary heartbeat upsert/delete, and `PENDING_WAKE` write;
- the Supervisor prohibition on positive-timeout/looped `wait_threads`;
- current Required GO IDs and each GO's versioned Required CELL IDs.
- current `DEVICE_CAPACITY_PROFILE`, `CUMULATIVE_ENGINEERING_LOAD`, and latest
  capacity-gate references.
- a role-wide Pin policy that is forbidden by default and never inferred from task
  creation, dispatch, activity, blocking, rework, verification, or importance.

Every capability must be `AVAILABLE`. Missing, `PENDING`, or `UNAVAILABLE` fails
closed. No capability authorizes guessed IDs or a replacement Checker.

## Hard rule 1: Worker-only wake ladder

### Frozen scope and message

Each ladder binds:

```text
RUN_ID
GO_ID
CELL_ID
CELL_ORDINAL
REQUIRED_CELL_TOTAL
ROUND_ID
CHECKER_THREAD_ID
CHECKER_HOST_ID
DELIVERY_STATE
```

Canonical runtime message:

```text
<GO_ID> CELL <ordinal>/<required-total> <state>，请检查
```

Allowed states are `已交付`, `BLOCKED`, and `EXECUTION_FAILURE`. Every level uses
the same scope, position, round, Checker binding, and message. Rework does not
increment ordinal or accepted count.

### Level 1 — T+0

Worker sends to the frozen Checker task and waits for ACK for at most 120 injected
seconds.

### Level 2 — T+2

Worker reads/lists the original task, checks existence, host, archive, and running
state, may unarchive the original task, re-resolves the same Checker from the frozen
registry, and resends. It never guesses an ID or creates a substitute. The bounded
wait is at most 120 seconds.

`THREAD_NOT_FOUND` records failure and proceeds without role creation.

### Level 3 — T+4

Worker upserts one deterministic temporary `CHECKER_WAKE_HEARTBEAT` derived from
Run, GO, CELL, Round, and Checker binding. Heartbeat count is exactly one. The third
bounded wait is at most 120 seconds.

Checker's first action is:

```text
WAKE_ACK <RUN_ID> <GO_ID> <CELL_ID> <ROUND_ID>
```

Checker then deletes the temporary heartbeat.

### Level 4 — T+6

Worker writes one deterministic `PENDING_WAKE` with full scope, three attempt
records, errors, logical/wall times, and original Checker binding. A best-effort
notification is optional; notification failure does not invalidate the record.

The unique Patrol observes and alerts on the record. Patrol cannot repair, reassign,
validate, or close technical work. Closure requires the original Checker ACK or
formal Run termination.

### Stop and cleanup

A matching ACK or mechanical evidence that the original Checker started handling
the delivery immediately stops escalation. Later levels are forbidden. Temporary
heartbeat is deleted and any pending record is consumed/closed. Success never
causes duplicate implementation, validation, Worker, or Checker.

Only Worker may initiate the ladder. The method-owner task's final cross-task
receipt remains the unrelated plain text `完成，请检验`.

## Hard rule 2: Supervisor waiting

Supervisor may use `read_thread` or `wait_threads(timeoutMs: 0)` as an immediate
snapshot. It must not use positive-timeout `wait_threads`, loop it, wait for all
members, or make Patrol a waiting controller. After dispatch/control it ends the
turn.

Only Worker may perform the three ACK waits, one per level, each at most 120 seconds
against the single original Checker.

## Hard rule 3: Run Patrol

Each Run has one Patrol conversation and one Patrol heartbeat. Frozen difficulty
selects 10, 15, or 30 minutes.

Patrol mechanically observes only:

- unexplained loss of legal forward motion;
- unconsumed `PENDING_WAKE`;
- `spawn_agent`, `delegate_task`, hidden Agent, or background Agent evidence;
- positive-timeout/looped Supervisor `wait_threads`;
- duplicate Patrol conversation or heartbeat;
- Patrol still active after formal Run termination.

Normal running, formal pause, valid `BLOCKED`, and external-condition wait are not
anomalies. Patrol emits fixed status/evidence/alert codes only. It never checks
engineering progress or quality; changes product; repairs; routes; dispatches;
verifies; accepts; or calls `create_thread`, `fork_thread`, `spawn_agent`, or
`delegate_task`.

Terminal sequence:

```text
LOOP_TERMINAL confirmed
→ patrol heartbeat deleted
→ PATROL_CLOSED
→ patrol conversation archived
```

## Hard rule 4: Task and subagent definition

These are not subagents:

```text
GO
CELL
Round
plan step
subtask / 子任务
visible stable peer task with threadId in the same project sidebar
```

Only `spawn_agent`, `delegate_task`, hidden Agent, and background Agent are
subagent evidence. `create_thread` and `fork_thread` are separately forbidden to
Patrol but are not reclassified as subagents.

## Hard rule 5: Layered real-time progress

### Source of truth

Numerators come only from current, non-invalidated immutable receipts:

- CELL numerator: unique valid D1 PASS receipts for current Required CELL IDs;
- GO numerator: unique valid D2 PASS receipts for current Required GO IDs.

Denominators come only from current versioned Required sets in
`RUN_RUNTIME_CONTRACT`. A Baseline/manifest/graph amendment creates a new Required
set version and recomputes current numerators/denominators. Historical snapshots
remain append-only.

Canonical statuses:

```text
DELIVERED
D1_ACCEPTED
GO_CANDIDATE_READY
D2_VERIFYING
D2_VERIFIED
RUN_VERIFIED
OWNER_ACCEPTED
BLOCKED
REWORK
```

Generic `已完成` is forbidden across layers.

### Worker → Checker

Worker uses the scoped `GO-X CELL n/N ...请检查` message at every wake level.
`n` is the delivery position, not accepted work. Delivery does not change
`accepted_cell_count`.

### Checker local progress

Checker sends matching `WAKE_ACK` first, then:

```text
收到 <GO_ID> CELL <n>/<N>，开始检查
```

After D1:

- PASS: `<GO_ID> CELL验收 <a>/<N>` plus next-CELL/GO-candidate state;
- FAIL/REWORK: accepted remains `a/N`, current CELL enters `Rxx`;
- BLOCKED: accepted remains `a/N`, current blocker shown.

Only the first current valid D1 PASS for a Required CELL increments the numerator.
Duplicate receipts, delivery, green tests, checking, and rework do not.

### Checker → Supervisor

Checker emits no per-CELL forwarding. When every current Required CELL of one GO
has valid D1 PASS and an immutable GO Candidate exists, it emits one milestone:

```text
GO <ordinal>/<required-go-total>；本GO CELL <N>/<N>已验收；
当前状态=GO_CANDIDATE_READY
```

`GO_CANDIDATE_READY` and `D2_VERIFYING` are not `D2_VERIFIED`. Only D2 PASS creates
the latter.

### Supervisor → Owner-visible progress

Supervisor reports only material GO, Run, D3, or Owner-Acceptance changes. It shows:

- current GO D1-accepted CELL count and Required CELL denominator;
- D2-verified Required GO count and Required GO denominator;
- D3 state;
- Owner Acceptance state;
- current Required-set version.

It does not relay Worker deliveries or Checker inspections.

### Other roles

Verifier emits formal D2/D3 verdicts only. Patrol emits no engineering progress.
No role outside SLK duplicates Checker/Supervisor reporting.

## Hard rule 6: Device and cumulative engineering load

### Versioned capacity facts

Before Run/plan freeze, Supervisor creates one versioned
`DEVICE_CAPACITY_PROFILE`. It contains verifiable numeric or enumerated facts:

- CPU model/logical cores and measured or conservative command capacity;
- available RAM;
- applicable GPU model and VRAM, or explicit `NOT_APPLICABLE`;
- free disk and measured/conservative IO;
- network and external-service limits;
- allowed processes/ports;
- safe device concurrency;
- measured/conservative single-test, full-test, and build durations;
- context-token and evidence-size budgets.

Unknown, `PENDING`, zero where capacity is required, or free text such as “high
performance” fails closed.

Supervisor also versions `CUMULATIVE_ENGINEERING_LOAD`, binding:

- accepted baseline file/dependency scale;
- measured full-regression and build duration;
- peak memory and disk growth;
- evidence/hash volume;
- context restoration load;
- external tool/browser/service cost;
- retry/rollback history and cumulative coupling.

It is updated at Run freeze, every important SLK GO boundary, Required-set
amendment, and material measured deviation. SLK has no Level or Graph boundary.

### Total-cost CELL estimate

Each planned CELL binds numeric estimates for:

- implementation, inputs, dependencies, outputs;
- build/test matrix and Checker independent reproduction;
- affected regression;
- evidence, hashes, cleanup;
- context loading;
- external tools/services;
- rollback/retry;
- coupling to the accepted baseline;
- peak RAM/disk and required device concurrency.

Line count and file count are descriptive only. A small diff with full regression
may be a heavy CELL.

### Capacity gate

Before every dispatch, Checker mechanically verifies the Supervisor-frozen
`CELL_CAPACITY_GATE`. Allowed outcomes:

```text
PASS
SPLIT_REQUIRED
CAPACITY_BLOCKED
```

Only `PASS` has `dispatch_allowed: true`.

`SPLIT_REQUIRED` freezes successor CELLs before dispatch. Every successor is
independently deliverable and independently D1-checkable with explicit dependencies.
All successors retain the original GO outcome and acceptance hash. Splitting does
not create a subagent, new Worker, or new GO, and never weakens verification.

`CAPACITY_BLOCKED` follows existing authority routes; Worker is not asked to try.
Logical work parallelism is distinct from device-safe concurrency, and SLK remains
one Worker/one Active GO/strictly serial.

### Dynamic feedback and post-dispatch defects

Measured command duration, memory peak, regression growth, dependency/file/evidence
scale, and context cost update the next load version and re-check all undispatched
CELLs. Later CELLs become smaller or receive larger verification budgets unless
current evidence proves capacity remains safe.

Worker that encounters scope beyond the frozen budget does not continue, self-split,
or create another Worker/subagent. It emits `CELL_SCOPE_EXCEEDED`, preserves one
immutable checkpoint/evidence package, and returns to the original Checker and
Supervisor planning authority.

A split first discovered after dispatch emits `POST_DISPATCH_CELL_SPLIT` as a
planning defect. Three or more successor CELLs additionally emit
`CELL_OVERSIZE_SEVERE` and require remaining-plan and device-budget re-evaluation.
Successor counts 6, 7, and 8 must always trigger the severe gate.

### Progress integration

Pre-dispatch splits or Required-set revisions create a new set version. Checker and
Supervisor immediately display the new denominator/version and recompute current
receipt-derived numerators. Historical `25/30` snapshots remain history and are not
current truth. Splitting alone adds no accepted progress.

## Hard rule 7: Owner-only task Pin authority

The three SLK Control responsibilities and Worker are denied
`set_thread_pinned(true)` by default. Run Patrol is non-technical and its Pin/Unpin
denial is validated separately. Creating or dispatching a role, entering ACTIVE, waiting,
blocking, reworking, verifying, reaching a milestone, or declaring a project
important never grants Pin authority. The method cannot infer permission from Owner
viewing habits, durable roles, or task names.

A Pin is legitimate only when its provenance is either an Owner manual Codex UI
choice or an Owner authorization that names the exact task in the current Run.
`THREAD_PIN_AUDIT` preserves task identity, current pinned state, every observed Pin
and Unpin operation, provenance, authorization/evidence references, and Patrol's
fixed result. An Agent/method Pin without item-specific authorization emits
`UNAUTHORIZED_THREAD_PIN`; an unprovable source emits `PIN_PROVENANCE_UNKNOWN` and
notifies Owner. A later Unpin cannot erase the unauthorized Pin event.

Patrol adds mechanical Pin-state/provenance inspection to its minimum-error list.
It reports only the two fixed alerts and evidence. It never calls Pin or Unpin:
automatic Unpin could undo a legitimate Owner choice. Pin is independent of
archive/unarchive and all task lifecycle states, and cannot substitute for progress,
role binding, or recovery indexing.

## Supervisor REDO closure

- Any positive Supervisor wait alerts regardless of one-shot/loop placement;
  looped and wait-all forms also alert, while timeout-zero snapshots remain normal.
- Every Patrol cycle contains the seven fixed unique checks with enumerated
  findings, evidence, and fixed alerts; workload maps LOW/MEDIUM/HIGH to 10/15/30.
- GO candidate readiness is unique per Required-set version and binds the D1 event
  that completed its Required CELL set. Every D2/D3/Owner material verdict has
  exactly one later Supervisor progress event bound to its trigger event and receipt.
- Every Required-set version after the initial set begins with exactly one ordered,
  receipt-bound Supervisor amendment progress event.
- `RUN_RUNTIME_INDEX` is a lightweight completeness package that binds each formal
  RUN/GO/CELL/ROUND dispatch to a capacity PASS for that Round, wake, delivery
  progress, and the current complete Patrol cycle. It is not a session Runtime.

## Validator invariants

The runtime validator rejects:

- wake sender other than Worker or receiver other than original Checker;
- missing scope, noncanonical message, or changed identity across levels;
- waits over 120 seconds, wrong offsets, loops, or levels after ACK;
- guessed IDs, substitute roles, duplicate heartbeat, or missing pending record;
- unavailable readiness capability;
- positive-timeout/looped Supervisor wait;
- duplicate/misbound Patrol, wrong model, or Patrol authority/action overreach;
- false alarms for formal pause or legal blocker;
- unclosed Patrol after terminal state;
- delivery/check/rework incrementing accepted count;
- duplicate D1/D2 receipts incrementing counts;
- GO candidate represented as D2 verified;
- per-CELL Checker-to-Supervisor noise;
- stale denominator after Required-set amendment;
- free-text counters not reproducible from receipt sets.
- unknown or unverifiable device facts;
- a gate outcome inconsistent with numeric device/load/cost facts;
- dispatch without capacity `PASS`;
- a split that changes GO outcome/acceptance or weakens independent D1 checks;
- Worker self-splitting or continuing after `CELL_SCOPE_EXCEEDED`;
- post-dispatch split without planning-defect evidence;
- three-or-more successors without `CELL_OVERSIZE_SEVERE` and full re-evaluation;
- stale progress denominator after a capacity-driven split.
- method-role Pin capability enabled without item-specific Owner authority;
- Agent/method Pin evidence not retained as `UNAUTHORIZED_THREAD_PIN`, including
  Pin-then-Unpin sequences;
- pinned state with unknown provenance not reported as `PIN_PROVENANCE_UNKNOWN`;
- Patrol Pin/Unpin action or automatic cleanup of an unknown-provenance Pin;
- lifecycle or importance semantics treated as Pin authority.

All invariants remain active under `python -O`.

## Simulation gate

`RUNTIME_SIMULATION` requires PASS plus evidence for:

- level 1 success;
- level 1 failure then level 2 success;
- archive/host repair;
- thread not found without guessing/replacement;
- unique level 3 heartbeat and ACK cleanup;
- level 4 pending wake observed by unique Patrol;
- ACK stops escalation;
- mechanical evidence that the original Checker started also stops escalation;
- non-Worker ladder rejected;
- Supervisor wait detected;
- visible peer task and “子任务” not classified as subagent;
- prohibited subagent evidence rejected;
- normal pause not alerted;
- duplicate Patrol rejected;
- terminal heartbeat deletion and archive;
- Worker message scope and n/N;
- delivery does not increment acceptance;
- D1 PASS increments once;
- rework/duplicate receipts do not increment;
- GO candidate does not imply D2;
- milestone only at GO boundary;
- Supervisor layered global progress;
- amendment denominator recomputation;
- no duplicate progress noise;
- all wake levels preserve one progress identity.
- early small CELL PASS and the same surface change becoming `SPLIT_REQUIRED` after
  cumulative regression growth;
- low RAM/disk/concurrency rejection and unknown capacity fail-closed;
- no dispatch without capacity PASS;
- split retains GO outcome/acceptance and independent D1 checks;
- Worker cannot self-split;
- post-dispatch 3+, 6, 7, and 8 successors trigger severe/re-evaluation;
- measured peak feedback tightens undispatched budgets;
- logical parallelism stays distinct from device-safe concurrency;
- split amendment recomputes fifth-rule denominators without increasing accepted.
- creation/dispatch does not Pin; SLK technical roles and Patrol are denied in their
  distinct authority categories;
- Patrol itself cannot Pin;
- Owner manual or exactly authorized Pin is not misreported;
- Agent Pin emits `UNAUTHORIZED_THREAD_PIN`;
- unknown provenance emits `PIN_PROVENANCE_UNKNOWN` without automatic Unpin;
- Pin then Unpin retains the violation.

Formal dispatch requires current runtime contract and simulation PASS.

## Test strategy

Tests invoke the real CLI with YAML fixtures and an injected logical clock. New
behavior is proven RED on 2.4.0, then made GREEN minimally. Coverage includes
contract/version/topology, admission, wake timing and cleanup, Patrol boundaries,
receipt-derived progress, device/load capacity gates, post-dispatch severity, Pin
provenance/history, de-duplication, amendments, simulation completeness, and
optimized-mode negatives.

Repository verification retains root/install mirrors, Manifest hashes,
UTF-8/JSON/YAML parsing, Windows/Ubuntu configuration, identity, sensitive-content,
boundary, and whitespace checks.

## Migration

Active 2.4.0 Runs do not silently acquire 2.5.0 behavior. Migration freezes:

- a 2.5.0 runtime contract;
- original Checker thread/host binding;
- Required-set versions/hashes;
- one Patrol conversation/heartbeat;
- successful capability preflight;
- successful runtime simulation.
- current device profile, cumulative load, and PASS capacity gates for every
  undispatched CELL.
- default-deny method-role Pin policy and current Pin provenance audits.

Historical receipts and progress remain append-only.
