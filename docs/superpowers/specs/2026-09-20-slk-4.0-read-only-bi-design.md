# SLK 4.0 Read-Only BI Design

Date: 2026-09-20  
Status: accepted for implementation from the Owner's prior BI decisions

## Purpose

Build a standalone desktop BI that presents the accepted SLK 4.0 state core across all projects and Runs. The application is a presentation and navigation layer only. It does not dispatch work, acknowledge delivery, decide inspection results, repair communication, grant exemptions, write role facts, or modify the database.

## Chosen approach

Use a standalone Tauri 2 desktop application with a React 19 and Vite frontend. Its Rust commands call `slk-state-core` read projections directly using read-only SQLite connections. This is preferred over two rejected alternatives:

1. Embedding the feature into LCaS now would alter another active project and bind SLK delivery to LCaS timing.
2. A browser application plus local HTTP daemon would add a service, lifecycle, port, and security boundary that the state core does not need.

The standalone application keeps SLK deployable now and keeps its React feature components suitable for later LCaS rc.08 or rc.09 integration.

## Invariants

- `slk-state-core` remains the only interpreter of state.
- `slk-bi-query` remains the read API for other Agents.
- BI Rust commands expose only projections already available through the core.
- BI has no credential input and no mutation command.
- Supervisor, Checker, and Worker remain the only writers.
- Owner and all other Agents are read-only consumers.
- No background Agent, watcher role, scheduler, lease, or acknowledgement protocol is added.
- A stored activity event is not process-liveness proof.

The frontend owns view state only: selection, filters, theme, pane size, and refresh timing. It never derives a second domain state machine.

## Read contract

Tauri exposes these commands:

- `projects`
- `runs(project_id?)`
- `run(run_id)`
- `graph(run_id)`
- `roles(run_id)`
- `plans(run_id)`
- `events(run_id)`
- `evidence(run_id)`

Each command returns the same versioned JSON projection produced by `slk-bi-query`. A shared contract fixture proves CLI and Tauri parity. The frontend rejects unsupported schema versions before rendering domain fields.

The app resolves the machine-wide SLK config file and opens the configured database read-only for each refresh. It does not keep a write-capable database handle. Refresh occurs when the window regains focus, when the user requests it, and at a modest interval while visible. Hidden windows pause polling.

## Information architecture

### Global overview

The left project rail groups Runs by project. It supports exact-text search by project name, Run name, ID, role, model, and state. Compact rows show the current responsibility role, closure state, and last factual event time.

### Run view

The center pane keeps SLK's linear character visible:

1. Run identity and latest fact
2. current TOKEN responsibility strip
3. ordered GO list
4. ordered CELL list for the selected GO
5. authored event timeline

Inspections are facts in the timeline and node state. They are not buttons or new CELLs.

### Inspector

The right pane presents the selected node, role, plan revision, event, correction pair, or evidence record. It makes agent runtime, model, reasoning, session, endpoint version, and replacement or rebound history readable without exposing credentials.

## Status semantics

The UI uses exact, conservative language:

- `Responsibility: Worker` means the TOKEN points to Worker.
- `Started, not delivered` means an unfinished authored work event exists.
- `Candidate delivered` means a candidate handoff is recorded.
- `Awaiting D2` means Checker passed D1 and delivered the D2 handoff.
- `Closed` means `RUN_CLOSED` exists.

The UI does not display "working now" based only on elapsed time, an old event, a session title, or a process guess. A future Overwatcher may confirm reality by communicating with roles, but it remains outside BI mutation and outside this release.

## Visual system

The UI follows `DESIGN.md` and mirrors LCaS's product language without source coupling: dark and light solid surfaces, system sans and mono data type, compact 12-16 px scale, 4 px spacing base, restrained periwinkle-blue selection, clear semantic state colors, 6-12 px radii, and 120-200 ms state transitions.

It avoids hero metrics, repeated cards, decorative glow, fake terminal styling, and control-room theater. The dense project rail, serial track, factual timeline, and inspector are the product.

## Errors and empty states

- Missing configuration: explain that the state core has not been configured; do not configure it from BI.
- Empty root: show a clear no-Runs state.
- Locked or transient read: retain the last successful projection, label it stale, and retry only through normal refresh.
- Unsupported schema: stop field interpretation and show supported versus received schema.
- Missing evidence: show the durable record and failed verification without repairing or removing it.
- Partial query failure: keep unaffected panes usable and identify the failed projection.

## Security and permissions

- Tauri capabilities contain only the commands and minimal file-open behavior required by the read UI.
- No shell plugin, arbitrary command execution, network listener, updater, telemetry, or remote content is included.
- External file opening is limited to a durable evidence path returned by the core and revalidated beneath the configured data root.
- Error rendering redacts credentials and never prints environment secrets.

## Testing

1. Rust command tests prove read-only open mode, projection parity, schema errors, missing config, and absence of write APIs.
2. TypeScript contract tests prove every supported projection and reject unknown schema versions.
3. DOM tests cover global overview, Run selection, TOKEN ownership, serial GO/CELL ordering, role replacement/rebound, correction pairs, resource contention, evidence mismatch, empty, stale, and error states.
4. Static tests scan Tauri capabilities and frontend code for forbidden mutation commands and credential surfaces.
5. A production build and Tauri compile run from an external target directory.
6. Visual acceptance captures dark and light screenshots at desktop and compact widths and checks keyboard navigation, focus, contrast, overflow, and reduced motion.
7. Integrated acceptance points BI and `slk-bi-query` at the same two concurrent test Runs and proves matching identities, counts, TOKEN, closure, and evidence facts.

## Delivery boundary

This subsystem is complete when the standalone desktop application reads the accepted state core, presents every specified view, exposes no mutation path, passes integrated and visual acceptance, and can be packaged without modifying an SLK-managed product repository. LCaS embedding remains a documented future integration, not part of SLK 4.0 completion.

## Self-review

- No placeholders or deferred decisions remain in this scope.
- The architecture reuses the accepted projection model rather than creating another one.
- The app is read-only at UI, command, capability, and database layers.
- Status wording does not claim unproved liveness.
- Future LCaS integration is enabled but does not expand the current scope.
