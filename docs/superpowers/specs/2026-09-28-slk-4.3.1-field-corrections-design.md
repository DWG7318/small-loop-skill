# SLK 4.3.1 Field Corrections Design

## Scope

SLK 4.3.1 is a patch release over 4.3.0. It preserves the Codex Supervisor, OCRV Checker, DSH Worker, optional whole-Run Overwatcher, serial CELL/D0/D1/D2 topology, single TOKEN, schema v8, read-only BI, optional Temporal continuity and direct-mode fallback. It does not modify or resume any product Run.

## Corrections

1. DSH dispatch now proves the real Git worktree and common store are writable from the Worker boundary before native start. Unsupported linked-worktree layouts fail closed and direct the Run to a standalone writable clone.
2. Worker completion is a closed outcome contract. Non-completed outcomes preserve phase, cause and evidence and cannot carry a candidate. The installed immutable inspector produces one attempt-bound fact for Overwatcher observation.
3. Checker retains authority for `D1_FAILED`; only Supervisor may write a scope-, candidate-, attempt- and round-bound `REWORK_REQUESTED` after that exact failure.
4. Codex active-writer recovery follows bounded `thread/turns/list` pagination and creates at most one payload-hash-bound recovery message only after proving the exact current turn.
5. Each Overwatcher pause/resume occurrence has a distinct append-only incident identity. A normal observation cycle stays in the same foreground turn and immediately performs another bounded central-state wait instead of ending the turn.
6. OCRV review may be split into durable capacity-sized segments. Segment findings are evidence only; one aggregate review produces the sole D1 verdict. Timeout preserves completed segments and returns a truthful incomplete result.
7. Context restoration revalidates the Run, goal, plan, CELL/attempt and TOKEN from authoritative state so an old summarized topic cannot redirect the active Run.
8. One mechanically checked audit matrix binds every Skill to its contracts, producers, consumers and installed path and covers authority, outcomes, writable roots, timeouts, active-writer states, Overwatcher cycles, migration, package, BI and Temporal-off operation.

## Compatibility and deployment

No database migration is required. Explicit `4.3.0 -> 4.3.1` adoption preserves the exact Run ID, plan revision, TOKEN holder and sequence, roles/endpoints, D0/D1/D2 facts, candidate and attempt evidence, Overwatcher binding/history, product working tree and uncommitted product changes. Installing 4.3.1 alone never adopts or resumes a Run. Deployment is a transactionally verified machine-wide tool/Skill replacement; source, package and installed bytes must match their manifests.
