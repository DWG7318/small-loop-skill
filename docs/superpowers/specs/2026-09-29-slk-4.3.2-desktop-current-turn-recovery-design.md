# SLK 4.3.2 Desktop Current-Turn Recovery Design

Date: 2026-09-29
Status: Owner-approved

## Scope

SLK 4.3.2 is a narrow transport patch over 4.3.1. It preserves the Codex Supervisor, OCRV Checker, DSH Worker, optional whole-Run Overwatcher, serial CELL/D0/D1/D2 topology, one TOKEN, schema v8, direct communication and optional Temporal continuity. It adds no role, scheduler, daemon, heartbeat, state machine or product mutation.

The patch fixes one observed boundary: Codex Desktop owns the registered Supervisor thread writer, while a separate `codex app-server` process fails during `initialize` with `thread-store conflict ... already has an active writer`. Because the external process never reaches `thread/read`, the existing `recover-active-writer` path has no `active-writer.json` and cannot truthfully create native-start evidence.

## Considered approaches

1. Repeated external app-server retries are rejected. They contend for the same writer, cannot prove a turn and would violate the one-shot recovery rule.
2. A new MCP service, daemon or coordinator is rejected as disproportionate and outside the patch boundary.
3. A two-phase Desktop-host bridge is selected. The existing Codex Desktop host observes and injects through native app tools, while `slk-transport` freezes, validates and persists the closed evidence.

## Closed bridge

`prepare-desktop-current-turn` accepts only the immutable original Checker-to-registered-Supervisor delivery. The original must have failed with `CODEX_ACTIVE_WRITER_UNRESOLVED`, must have no start proof, and must retain the exact endpoint and envelope. Preparation creates one immutable recovery request under `recovery/desktop-current-turn`, including a new recovery message ID, random challenge, original identity fields, endpoint/envelope/payload hashes, registered thread ID and canonical recovery prompt. Repeated preparation returns the byte-identical request; conflicting evidence is rejected.

The active Codex Desktop host then performs one bounded native sequence:

1. Read the registered target and prove exactly one current `inProgress`/`active` turn.
2. Send the canonical recovery prompt through `send_message_to_thread`.
3. Read the same target again and prove the same turn now contains exactly one new platform `functionCallOutput` item for `codex_app.send_message_to_thread`, whose output text is the canonical prompt.

The host supplies a closed receipt containing its own Desktop thread/turn identity, the before and after target observation, the new platform item ID, request hash and prompt hash. `complete-desktop-current-turn` requires a real Codex Desktop shell identity, validates every receipt field against the immutable request and original delivery, and writes `host-receipt.json`, `recovery.json` and `started.json` exactly once. The start receipt uses the new recovery message ID and binds `recovery_of_message_id` to the original. It does not move TOKEN; the original Checker remains responsible for `commit-delivery-start` with its credential.

A UI state, Owner activation, ordinary visible message, successful `send_message_to_thread` call without target readback, free-form receipt, changed turn, changed hash or missing platform item never creates `started.json`.

## Diagnostic output bound

The JSON-RPC client keeps full protocol behavior but bounds persisted stdout/stderr diagnostics. Oversized lines are replaced by a length-and-SHA-256 record with a small prefix; total retained diagnostic bytes are capped and followed by an omitted-byte/line digest summary. Small transcripts remain byte-for-byte readable for existing tests. This prevents a failed writer conflict from producing hundreds of megabytes while retaining request IDs, methods, error text, sizes and hashes.

## Compatibility and release

No database migration is added. Explicit 4.3.1-to-4.3.2 adoption remains available, but the transport patch may recover an exact preserved 4.3.1 unresolved attempt under Owner authorization without first rewriting Run history. Installation alone does not adopt, resume or mutate any Run.

Release validation must include the original initialize-conflict shape, bridge identity/hash/turn negatives, single-use behavior, bounded transcript evidence, transport/state regressions, repository/Manifest validation, deterministic package verification, installed-byte verification and one real Codex Desktop host integration using a disposable attempt outside every product Run.
