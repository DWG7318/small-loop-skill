# SLK 4.0 Resource Continuity Design

Date: 2026-09-20  
Status: Owner-approved design, pending implementation plan  
Target: unreleased SLK 4.0.0 candidate

## Problem

SLK 4.0 can record `RESOURCE_CONTENDED` and `RESOURCE_RECOVERED` without moving the SLK TOKEN or miscounting a D1 rework. It does not yet prevent the most common construction collision or restore the blocked command itself. Real Run records show that Cargo build-directory contention, inactive stale leases, Windows/WSL target reuse, and stale generated binaries can stop construction or produce misleading evidence.

The missing method boundary is a short, static resource check before construction plus an executable Cargo isolation and recovery path. This must not turn Supervisor into a resource monitor or add a dynamic resource-management system.

## Decisions

1. Add one SLK-only child Skill named `slk-guard-resources`.
2. Keep the planning checklist static. The only named historical item is Cargo/Rust. A second generic question asks whether the Run has another obvious exclusive resource.
3. Apply the checklist once while the Run plan is formed and confirm it once during Supervisor Grill. Revisit it only when the Run is deliberately replanned; do not maintain a live resource register.
4. Add a small `slk-cargo` executable for Cargo commands. It is a command wrapper, not a role, scheduler, watcher, daemon, resident lock manager, inspection layer, or CELL.
5. Preserve the current three roles, serial GO/CELL Loop, D0/D1/D2, rework, exemption, transport, TOKEN, and state authority.
6. Include this work in the unreleased 4.0.0 candidate rather than creating a separate method generation.

## Skill placement and routing

### `slk-plan-run`

After the Run boundary and linear GO route are known, but before inspection design, model selection, and CELL sizing, route once to `slk-guard-resources`.

The planned order becomes:

```text
Run boundary
→ linear GO route
→ static resource check
→ D0/D1/D2 design
→ role-model selection
→ initial CELL sizing
```

The Run plan records only applicable decisions, such as the allocated Cargo target root. It does not contain a growing resource ledger.

### `slk-grill-supervisor`

Add one understanding question: whether the current Run uses Cargo or another obvious exclusive resource, and which isolation or ordering decision is already in the plan. Supervisor confirms or corrects this once before construction. This is not continuing patrol.

### `slk-guard-resources`

The new child Skill contains the one authoritative static checklist:

1. **Cargo/Rust:** if the Run invokes Cargo, allocate a repository-external target directory owned by the Run and use `slk-cargo` for Worker and Checker Cargo commands.
2. **Other obvious exclusive resource:** ask once whether the Run uses a fixed port, shared database, shared output location, GPU or physical device, shared account, or another resource that cannot safely run concurrently. When applicable, use the Cargo pattern: isolate by Run; otherwise order only the conflicting command; recover only the current Run's resource.

It must explicitly state that absence of another known resource ends the check. It must not encourage exhaustive discovery, speculative controls, proof collection, another planning phase, or a resource-only CELL.

### Runtime references

Worker and Checker continue using the existing `resource-contention.md` reference only when contention actually occurs. Its Cargo wording changes from per-Run/CELL target allocation to per-Run allocation. The reference points to `slk-cargo` and keeps the existing rules: the current role retains the TOKEN; contention is not product failure; unknown locks are not declared stale; unrelated processes are not terminated; recovery resumes the same CELL and inspection node.

The main SLK router adds `slk-guard-resources` to its situational routes and collection count. It does not duplicate the checklist body.

## Cargo execution design

### Invocation

`slk-cargo` receives the current project ID, Run ID, role instance, GO, CELL, project root, and the exact Cargo arguments. It resolves the configured SLK data root and uses:

```text
<SLK data root>/runtime/cargo/<project-id>/<run-id>/primary
```

Worker and Checker in one Run reuse `primary`. Different Runs never share a target directory. Cargo's normal shared `CARGO_HOME` remains reusable; the tool does not clone the dependency cache for every Run.

The target directory is disposable runtime data. It is excluded from evidence copies, deterministic Run exports, BI state, repository manifests, and project Git.

### Normal execution

The tool executes the requested Cargo command without changing package selection, features, profile, lockfile policy, offline policy, test filters, or test-thread settings. It streams stdout and stderr unchanged and returns Cargo's real exit status.

The tool may add only the resolved target directory. An explicitly incompatible caller-provided target directory is rejected rather than silently overriding the Run isolation boundary.

### Contention classification

The wrapper distinguishes:

- an explicit Cargo build-directory lock wait;
- an explicit Cargo package-cache lock wait;
- a Windows file-in-use/sharing violation for an artifact inside the current Run target;
- a normal compiler, linker, test, dependency, configuration, or product failure.

It does not classify silence, duration alone, or a generic nonzero exit as resource contention.

### Recovery

- A package-cache lock remains with Cargo's normal coordination; the wrapper exposes the exact waiting fact and does not switch offline mode or create another Cargo home.
- A build-directory lock or current-target Windows sharing violation may retry the same command once in a fresh recovery target below the same Run runtime directory.
- The wrapper may stop only the Cargo child process it started when that child is explicitly waiting for the conflicting build-directory lock. It never terminates another Cargo, rustc, test, application, or unrelated process.
- It never deletes an unknown lock or another Run's target. Stale cleanup requires positive evidence that the recorded owner no longer exists.
- If recovery succeeds, execution continues from the same CELL. If it cannot recover safely, the command returns a precise resource blocker; the current role retains responsibility and uses the existing Checker/Supervisor route.

### State facts

When the caller provides a valid active role credential, `slk-cargo` appends the existing `RESOURCE_CONTENDED` and `RESOURCE_RECOVERED` facts with the resource class, primary/recovery target identity, command identity, and observed evidence. It does not hand off the TOKEN, change plan revision, increment rework, declare D0/D1/D2, or infer that another process is alive.

If state recording fails, the Cargo result remains truthful and the tool reports the state-write error separately. A state-write failure does not convert a failed Cargo command into success or a successful Cargo command into verified SLK closure.

## Static checklist boundary

The checklist is intentionally short because current records establish Cargo as the repeated system-level construction resource problem. Ports, databases, GPUs, devices, shared accounts, and output directories remain examples under the single generic question until future Run-record review shows a repeated incident worthy of a named item.

Future checklist additions require evidence from completed SLK records and a later SLK version. Individual Supervisors do not expand the global checklist during a Run.

## Verification

Implementation acceptance covers:

1. two simultaneous Runs in one Rust repository use different target roots and both complete;
2. Worker and Checker in one Run resolve the same primary target;
3. an explicit build-directory lock triggers a recovery target without killing the lock owner;
4. a current-target Windows sharing violation can retry without deleting the primary target;
5. a package-cache wait is reported without changing `CARGO_HOME` or forcing offline mode;
6. a normal compile or test failure remains the original Cargo failure and is not mislabeled contention;
7. RESOURCE events leave TOKEN owner, sequence, CELL, and D1 rework count unchanged;
8. runtime target paths stay outside the repository, Manifest, exports, and evidence;
9. Supervisor planning/Grill guidance is static and the collection remains one main Skill plus SLK-only children;
10. all existing Python, Rust, BI, repository, Manifest, and Skill validation remains green.

## Non-goals

- no dynamic resource inventory;
- no Supervisor polling or continuous monitoring;
- no automatic process killing outside the wrapper-owned waiting child;
- no global Cargo serialization lock;
- no per-CELL target directory;
- no automatic `--offline`, feature, profile, or test-scope change;
- no resource scheduler, reservation service, new Agent, new role, new inspection, or new CELL;
- no attempt to automate every possible port, database, GPU, device, account, or quota conflict in this version.
