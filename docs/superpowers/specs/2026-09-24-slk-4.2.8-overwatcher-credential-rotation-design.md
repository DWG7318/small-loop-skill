# SLK 4.2.8 Overwatcher Credential Rotation Design

## Problem

An ACTIVE Overwatcher binding can become unusable when a caller persists the non-secret credential identifier instead of the one-time write credential returned by `bind-overwatcher` or `replace-overwatcher`. The secret is intentionally unrecoverable. Existing recovery changes role/session identity and requires a prior continuity violation, but the invalid credential cannot record that violation. This creates a method-level deadlock without indicating a product defect.

## Chosen boundary

Add one Supervisor-authenticated `rotate-overwatcher-credential` state action. Its closed request binds the exact Run, binding revision, runtime revision, role instance, Session, foreground turn, current credential ID, evidence hash, reason and timestamp. It is valid only for an open Run with the same ACTIVE Overwatcher binding and supports effective method versions 4.2.7 and 4.2.8 so a stranded 4.2.7 Run can recover before adoption.

The transaction replaces only the binding's credential ID/hash, advances the runtime revision, and appends one immutable credential-rotation receipt. It does not change role, Session, turn, binding revision, endpoint, cadence, continuity, TOKEN, CELL/GO state or engineering history. The old write credential stops authenticating immediately.

## Secret delivery and response vocabulary

The command returns the new secret once as `overwatcher_write_credential` and its non-secret identity as `overwatcher_credential_id`. `bind-overwatcher` and `replace-overwatcher` use the same names and remove the ambiguous `overwatcher_credential` / `credential_id` pair. Every issuing response states `write_credential_delivery=ONE_TIME_NON_REPLAYABLE`.

Rotation request replay is explicitly rejected after success because SLK never persists plaintext write credentials. Storing an encrypted replayable secret would add a key-management system and is rejected as disproportionate. The caller must capture the first successful response atomically, retain the full `slk_...` write credential in its secure runtime secret channel, and immediately call `authenticate-role` with the same Run and role instance before proceeding.

## Audit schema

SQLite schema v8 adds append-only `overwatcher_credential_rotations`. Each row records the rotation ID, exact binding identity, old/new credential IDs, resulting runtime revision, evidence path/hash, reason and time. Update/delete triggers preserve the receipt. No plaintext secret is stored.

## R3B recovery sequence

1. The current Supervisor queries the canonical Run and obtains exact binding revision 4, runtime revision 79, role/session/turn and current credential ID.
2. It hashes a bounded evidence file explaining the lost/mis-saved credential and invokes `rotate-overwatcher-credential` under the Supervisor write credential.
3. It captures `overwatcher_write_credential` once and immediately validates it with `authenticate-role` for the same Run and Overwatcher role instance.
4. The same Overwatcher Session records a complete cycle at the returned runtime revision with the new credential.
5. The Supervisor adopts 4.2.7 → 4.2.8 using `PRESERVED_ACTIVE`, then records the already-earned product D2 through the existing path.

No direct SQLite edit, fabricated cycle, fabricated continuity violation, replacement role/session, product mutation or automatic D2 is permitted.

## Alternatives rejected

- Extending `replace-overwatcher`: changes identity/binding and preserves the continuity deadlock.
- Persisting or decrypting old secrets: breaks the existing one-way credential boundary and adds key management.
- Letting Overwatcher self-rotate: impossible when the credential is lost and weakens Supervisor authority.
- Reusing a generic work event: would incorrectly alter engineering history.

## Acceptance

- A Supervisor can rotate the exact ACTIVE binding with no prior cycle or continuity violation.
- Wrong actor, stale runtime/binding, wrong role/session/turn/current credential ID, closed/non-ACTIVE binding, malformed evidence and replay all fail closed.
- The new credential authenticates immediately; the old credential and credential ID used as a secret both fail.
- TOKEN, binding identity/revision, continuity and engineering facts are unchanged; runtime revision advances exactly once.
- Issuing response fields are unambiguous and no plaintext secret enters SQLite, exports, logs or BI.
