# SLK 4.3.0 Optional Temporal Continuity Design

**Date:** 2026-09-28
**Status:** Owner-approved direction, implementation candidate

## Purpose

SLK 4.3.0 adds two reusable, optional Temporal templates so one Run can keep a durable record of startup and communication continuity without turning SLK itself into a workflow engine. It also closes the narrow field defects found by `SLK-RUN-LCAS-RC08-OUTPUT-LIMIT-SAFE-RECOVERY` that are not already covered by 4.2.11.

The existing method remains authoritative: Codex is Supervisor, OCRV is Checker, DSH DeepSeek V4 Flash is Worker, Overwatcher is optional, the topology is `Run → CELL`, D1 belongs to Checker, D2 occurs once after all required CELLs, and BoM remains disabled.

## Chosen Architecture

Ship a small optional Python integration under `integrations/temporal/`:

1. `StartSlkWorkflow` is the reusable **启动 SLK** template. It accepts one closed startup request, runs one adapter activity that validates/finalizes existing SLK readiness, and starts exactly one `RunSlkWorkflow` child with a deterministic workflow ID derived from `run_id`.
2. `RunSlkWorkflow` is the reusable **进行 SLK** template. It does not reproduce CELL, D0, D1, D2, TOKEN, role or BI state. It durably tracks only a closed communication envelope: requested delivery, matching native-start acknowledgement, timeout, recovery request, recovery acknowledgement and terminal closure.
3. Activities are adapter boundaries. The template package defines typed contracts and sample no-product adapters; a deployment supplies activities that call existing `slk-state` and `slk-transport` interfaces. Agent judgment remains in the Skills and the existing roles.
4. Temporal is optional. Core SLK installation, Skills, state, transport and BI work when the SDK or server is absent. The local package distributes the templates and documentation but does not install or start Temporal, Docker, a service, a daemon or a new Agent.

This is preferred over documentation-only examples because the contracts and workflows can be imported and tested. It is preferred over embedding Temporal into `slk-state` or `slk-transport` because that would make every Run depend on an external service and duplicate existing authority.

## Workflow Contracts

### Startup

`StartSlkRequest` binds `run_id`, `method_version`, `runtime_revision`, immutable role endpoint references, optional Overwatcher endpoint, task queue and one idempotency key. Empty identities, duplicate engineering roles, a changed request under the same workflow ID, or an unsupported version fail closed.

The startup activity returns a hash-bound readiness receipt. The workflow starts one child with ID `slk-run/<run_id>` only after that receipt passes. Replay of the same request returns the same startup result; changed replay is rejected.

### Communication continuity

`RunSlkWorkflow` accepts a `request_delivery` update containing one exact `message_id`, sender, receiver, scope, payload SHA-256 and source `runtime_revision`. It runs the configured delivery activity once per deterministic operation key and waits for a matching `native_started` signal. A tool return or terminal result is not an acknowledgement.

If no matching acknowledgement arrives within the configured bounded timeout, the workflow records `RECOVERY_REQUIRED` and runs the recovery activity. When a Run has an Overwatcher, the activity routes the exact incident to that bound Session; otherwise it invokes the existing sender-owned recovery boundary. Recovery cannot change receiver, payload, CELL/attempt or message identity. A matching acknowledgement stops further recovery immediately. If the platform has no verified continuation route, the workflow remains truthfully blocked instead of inventing progress.

The workflow exposes a compact query snapshot for operators. It never edits BI, moves TOKEN, decides PASS/FAIL/INCOMPLETE, creates a role, chooses the next CELL or replaces Supervisor judgment.

## Field Corrections

Most RC08 findings are already correctly implemented by 4.2.10/4.2.11 and receive regression coverage only: semantic `D1-A/B/C...` inspection segments, one aggregate D1, INCOMPLETE versus FAIL, low-only observations, compact evidence indexes, active-writer direct recovery, standard resource guards, and D2 after all CELLs.

The remaining source changes are deliberately narrow:

- `register-evidence` reports an invalid `evidence_id` as an explicit identifier-field error, including the accepted ASCII character rule, before checking the source path.
- `revise-plan` rejects an empty snapshot, blank reason and a snapshot with no substantive difference from the current plan revision.
- Skill/state vocabulary uses the existing state event `REWORK_REQUESTED`; `D1_REWORK_DIRECTIVE` remains the transport payload type and is not described as a state event.
- Existing active-writer and evidence-index behavior receives direct regression tests from the RC08 evidence.

## D1 Evidence Budget

Checker performs one light capacity/evidence preflight before a potentially large D1. It may create as many sequential semantic inspection segments as the acceptance surface requires; no fixed count and no file-count split is allowed. All required segments remain in the same candidate and D1 attempt and produce one aggregate verdict.

The default handoff is a compact index containing command, exit status, summary, decisive failure tail when present, original path, byte count and SHA-256. Raw logs remain retrievable. Worker self-report is context, never the independent Checker conclusion.

## Compatibility and Deployment

The release target is 4.3.0 with SQLite schema v8 unchanged. Existing 4.2.11 Runs do not silently acquire Temporal. A Supervisor explicitly selects the optional Temporal mode when starting or adopting a compatible Run; otherwise all existing direct communication and recovery paths remain unchanged.

The package copies `integrations/temporal/` into the installed SLK share. SDK installation and a local or remote Temporal service are deployment choices outside the core installer. Windows local development may use the official standalone `temporal.exe`; Docker is neither required nor installed.

## Acceptance

- Core installation and all existing tests pass with no `temporalio` module and no Temporal server.
- Contract tests reject malformed startup, duplicate role identity, changed replay, mismatched acknowledgements, scope-changing recovery and progress inferred from a terminal result.
- Workflow tests prove one idempotent startup child, delivery → acknowledgement, timeout → recovery, acknowledgement stopping recovery, optional Overwatcher routing and truthful blocked state.
- Rust tests prove explicit `evidence_id` errors and substantive `revise-plan` validation.
- Repository, Manifest, JSON, Skill, Python `-O`, Rust, BI, package and installed-mirror gates pass.
- A portable local Temporal test may run with the official SDK/CLI, but no Docker runtime is installed, enabled or restored.

## Explicit Non-Goals

- No fourth engineering role, replacement Supervisor, Router, BoM route, heartbeat, scheduler or BI writer.
- No Temporal model of D0/D1/D2/TOKEN or automatic engineering decision.
- No mandatory Temporal dependency for ordinary SLK Runs.
- No LCaS product change and no real Codex/OCRV/DSH dispatch in repository tests.
