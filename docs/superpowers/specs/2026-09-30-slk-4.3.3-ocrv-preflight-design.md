# SLK 4.3.3 OCRV Preflight and Run Readiness Design

**Date:** 2026-09-30  
**Status:** Owner-approved for direct implementation

## Problem

SLK 4.3.2 labels OCRV review segments but does not constrain their real candidate scope. Every segment still reviews the same commit/range/workspace, and the aggregate review receives every full segment result again. Real RC08 evidence showed segment 001 naming one Rust file while OCRV reviewed four files, a completed blocking finding followed by segment 002, and final backgrounds of 8,771 and 16,162 characters against the 8,000-character adapter limit.

Run admission has a related gap: the plan freezes Codex Supervisor, DSH Worker and OCRV Checker identities, but no single executable readiness check proves their concrete adapter, endpoint, context/task capacity, writable workspace and required Skill/Tool surfaces. Optional features are also described in several places without one fail-closed Owner decision record.

## Invariants

- Preserve Codex Supervisor, OCRV Checker, DSH Worker, optional Overwatcher, CELL/D0/D1/D2, TOKEN and direct communication authority.
- OCRV remains the only D1 authority. Segment results are internal evidence; one final OCRV result remains the formal D1.
- Deterministic code measures paths, hashes, bytes, characters, preview scope and executable availability. Agent Skills retain semantic judgment.
- No daemon, heartbeat, new role, generic plugin system, automatic option enablement or second Checker.
- The closed LCaS source Run remains immutable.

## Run Readiness Gate

Add a dependency-free `slk-transport preflight-run` command with a closed JSON request/result contract. The request names exactly one Supervisor, Worker and Checker. Every role records expected and actual runtime/model, adapter command, endpoint artifact, context capacity, estimated task load, writable workspace and required Skill/Tool paths.

Each role receives exactly one status:

- `READY`: all deterministic facts pass;
- `REPAIR_NEEDED`: a reachable local fact such as a missing adapter, endpoint, Skill, Tool or writable path needs correction;
- `INCOMPATIBLE`: runtime/model mismatch or task load exceeds declared context capacity.

The overall result is `READY` only when all three roles are ready and every required optional feature has an Owner decision. The required option set is Ponytail, Temporal, Overwatcher, RTK, Probe CLI and BoM. Each decision is `ON`, `OFF` or `UNCONFIRMED`; only `ON`/`OFF` with a non-empty Owner evidence reference completes preparation. Additional future options are allowed but follow the same rule. The result gives only deterministic gaps and minimal repair suggestions; it does not dispatch, split CELLs or judge engineering quality.

## Executable OCRV Preflight

The supported OCRV adapter becomes a versioned SLK-owned integration file installed transactionally into the existing OCRV root. It accepts the closed D1 request plus a `--preflight` mode. Preflight:

1. validates candidate, criteria, evidence, capacity and optional real scope;
2. materializes the exact background that a model run would receive;
3. records UTF-8 character count, byte count and original evidence bytes;
4. compacts verbose evidence to a whitelist of candidate identity, ancestry, changed paths, test outcomes, source paths and SHA-256 while keeping original files untouched;
5. calls OCRV 1.12.7 `review --preview` with the exact candidate arguments and exclusions;
6. returns the actual preview inventory, selected reviewable paths, excluded paths, churn and hashes without calling the model.

The transport performs a full preview, then greedily creates as many ordered segments as needed from real selected paths, criteria and configured capacity. It preflights every proposed segment. A segment is launchable only when:

- its materialized background is within character and byte limits;
- its changed-line estimate is within the configured segment limit;
- preview succeeds;
- preview `will_review=true` paths exactly equal the segment manifest;
- all other selected candidate paths are explicitly excluded.

If one path or one criterion cannot fit, transport returns `OCRV_REVIEW_INCOMPLETE` before model start. It never silently widens scope.

## Segment Execution and Aggregate

Segments run sequentially. Each directory stores request, preflight, result, stdout, stderr and hashes. After a complete segment:

- `FAIL` with a HIGH/BLOCKER/CRITICAL finding stops before the next segment and produces a compact early-stop aggregate request;
- `INCOMPLETE` stops and remains a real incomplete D1 attempt;
- `PASS`, or a non-blocking finding that OCRV represents without a blocking severity, may continue.

Completed PASS segments are reusable only when candidate hash, include/exclude scope hash and criteria hash match exactly. Reuse remains internal and does not create a D1 verdict.

The final aggregate receives only a compact segment summary containing IDs, scopes, verdicts, reason codes, finding counts, blocking finding summaries and request/result SHA-256 values. It never receives segment result files as evidence. The original evidence index remains traceable by path and hash.

## Checker Capabilities

Add one small OCRV capability profile and concise Checker guidance. The profile discovers native OCRV preview, RTK and Probe CLI without installing them. Probe CLI is selected for multi-file/cross-module segments and invoked in bounded symbol mode; its output is stored separately and only a bounded digest may enter the background. RTK is selected only when Checker executes a supported high-noise command; the original log remains authoritative and native-command fallback is mandatory. Missing optional tools never weaken D1 and never block an otherwise valid native review.

Ponytail remains an Owner-authorized optional Skill, not a hook, MCP, proof source or automatic D1 input.

## Installation and Rollback

The OCRV installer stages and verifies the adapter, wrapper, recovery companion and capability profile before replacement. It backs up all managed OCRV files, writes a receipt with old/new SHA-256 values, verifies the active copy and rolls back on any mismatch. The global SLK package keeps its existing transactional backup/install behavior. Windows PowerShell processes remain headless.

## Acceptance

- A descriptive segment whose preview still selects the whole candidate is rejected.
- An oversized final background fails before model process creation.
- Dynamic N segments each have preview scope identical to their manifest.
- A blocking finding prevents the next segment process from starting.
- Aggregate evidence contains no full segment result body or path injection.
- Missing critical capability for any of the three roles prevents readiness.
- Any required option left unconfirmed prevents readiness.
- OCRV and global deployment prove backup, hashes, verification and rollback paths.
- Full Python, Python `-O`, Rust, repository, package and isolated OCRV integration gates pass.

## Self-review

- No placeholders or deferred design choices remain.
- The design changes only SLK-owned readiness and OCRV integration surfaces.
- Preview and capacity facts are deterministic; D1 semantics remain with OCRV.
- Optional tools remain optional and Owner-controlled.
- No new runtime service, role or persistent scheduler is introduced.
