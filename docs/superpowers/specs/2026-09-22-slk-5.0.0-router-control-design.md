# SLK 5.0.0 Router Control Design

**Date:** 2026-09-22
**Status:** Owner-approved direction; implementation candidate

## Purpose

SLK 5.0.0 separates engineering work from Loop control. Worker and Checker do their bounded work and return closed results. A new Router role owns TOKEN movement, authoritative runtime-state advancement, exact next-role activation, stalled-transition detection, and the state read by LE BI. Supervisor remains the only planning and exception-decision authority.

This is a topology change and therefore a major version. It is deliberately narrower than Temporal: one serial SLK Run, one current transition, one SQLite authority, one existing transport layer, and no general workflow language.

## Topology and authority

```text
                         decision required
                    +------------------------> Supervisor
                    |                              |
                    |                          closed decision
                    |                              v
Worker result ---> Router ---> Checker work ---> Router
      ^                |                              |
      +----------------+<----- Checker result -------+
             exact next activation

LE BI <--- read-only projection of Router-committed state
```

- **Supervisor** freezes the Run plan, decides genuine ambiguity, scope changes, exemptions, recovery policy, and D2. It does not poll members or manually relay ordinary CELL traffic.
- **Router** is a formal non-engineering control role. It validates closed results, applies the versioned transition table, advances TOKEN/state, activates the exact next registered endpoint, detects abnormal silence, and wakes Supervisor only when a decision is required. It cannot author D0, D1, D2, candidate content, exemptions, or plan meaning.
- **Checker** calibrates the next planned CELL, performs isolated D1, and returns a closed readiness/verdict result. It does not activate Worker, move TOKEN, update BI, or contact Supervisor directly.
- **Worker** implements one CELL, performs minimum D0, and returns a closed candidate/blocker result. It does not activate Checker, move TOKEN, update BI, or create work.
- **LE BI** remains read-only. Router updates the authoritative state; BI never receives a write API.

## Supervisor-hosted compatibility binding

Until LCaS can create a dedicated Router task, each 5.0 Run uses `SUPERVISOR_HOSTED` binding:

- Supervisor and Router share one visible Codex task and native endpoint.
- They have different `role_instance_id`, credentials, event authorship, and authority.
- Router actions are deterministic runtime actions under the Router identity; Supervisor decisions are explicit Supervisor results. Sharing a task never converts one into the other.
- A future `DEDICATED` binding may rebind the same Router role to a separate visible task without changing Run semantics.

The state core creates the compatibility Router identity during 5.0 Run initialization and returns both credentials. It never infers Router authority from a Supervisor credential.

## Closed results and transition table

Roles submit immutable results; they do not mutate projected Run state. Each result binds schema version, Run, plan revision, GO, CELL, attempt, producer role instance, result kind, payload hash, evidence references, and time. Duplicate identity with different content is rejected; exact replay is idempotent.

The Router accepts only these ordinary transitions:

| Current accepted result/state | Router action |
| --- | --- |
| `SUPERVISOR_RUN_READY` | activate Checker for `CELL_READY` |
| `CHECKER_CELL_READY` | activate Worker for the same CELL |
| `WORKER_CANDIDATE_READY` | activate Checker for isolated D1 |
| `CHECKER_D1_FAIL` | activate Worker for the same CELL/next attempt |
| `CHECKER_D1_PASS` with another required CELL | activate Checker to prepare that exact next CELL |
| final required `CHECKER_D1_PASS` | activate Supervisor for D2 |
| `SUPERVISOR_D2_FAIL` with an explicit route | apply that route through the same table |
| `SUPERVISOR_D2_PASS` | close the Run and stop Router |

`BLOCKED`, invalid/missing results, plan-version conflicts, exhausted transport recovery, competing legal routes, scope change, exemption, replacement, and lifecycle correction activate Supervisor with evidence. Router never chooses product meaning from free text.

## Transaction and TOKEN semantics

Every activation is a recoverable two-phase transition:

1. Router records one idempotent `PREPARED` transition bound to the accepted source result, exact target identity/endpoint, immutable envelope hash, and proposed TOKEN sequence.
2. Existing `slk-transport` starts that exact endpoint. No guessed task, replacement role, or title lookup is permitted.
3. Matching native start proof atomically commits `TOKEN_HANDED_OFF`, the new expected action, and the BI-visible state. A failed start leaves the previous committed TOKEN unchanged and records the transition failure.
4. Router consumes the source result exactly once. Restarting Router resumes the prepared transition instead of repeating engineering work.

Only Router may commit TOKEN transitions. TOKEN still names the role responsible for the current engineering node; Router is the writer, not necessarily the holder.

## Continuity without an Agent heartbeat

`slk-router` is a small local, headless, deterministic runner over SQLite and the existing transport adapters. It is not an AI conversation, scheduler platform, MCP server, or general workflow engine.

- Exactly one leased Router runner may control a Run. A restart resumes durable state.
- The runner observes only closed results, immutable transport evidence, current native status where supported, explicit pause/block state, and deadlines. It does not read role reasoning or poll chat text.
- The active transport call already waits for the exact target turn/result within a bounded role deadline. Missing result, wrong identity, timeout, or terminal failure becomes a durable Router incident and wakes the registered Supervisor endpoint.
- `PAUSED`, `WAITING_EXTERNAL`, declared `BLOCKED`, and an outstanding Supervisor decision are legal stops. `ACTIVE` with neither a valid result nor live native execution after its deadline is `STALLED`.
- No role uses `wait_threads`. No AI heartbeat is evidence of progress.

The first implementation may be started/stopped by Supervisor-hosted commands, but progress after start is performed by the headless Router runner. The runner shuts down after terminal Run state.

## Interpretation Eval

A single versioned, data-driven Eval covers the four roles. It emphasizes known failure modes rather than general comprehension:

- Supervisor must not wait, relay ordinary CELL traffic, perform D1, write Router state, or treat visibility as execution.
- Router must not create engineering judgments, accept free-text progress, skip native start proof, guess endpoints, duplicate a transition, or keep obsolete Runs active.
- Checker must not dispatch directly, move TOKEN, increase accepted progress before D1 PASS, inspect Worker reasoning before isolated D1, or escalate routine results directly.
- Worker must not split/create work, move TOKEN, self-accept, contact Supervisor for ordinary flow, or stop after an intermediate command.

The validator uses a closed answer set and stable case-pack hash. Project names, paths, and harmless presentation variants cannot change the expected decisions; missing, duplicate, stale, extra, case-mutated, or whitespace-mutated identifiers fail closed.

## Run lineage and LE BI

Independent Runs in one project remain independent. A corrective successor uses one explicit predecessor-successor edge and one atomic lifecycle operation that archives the predecessor while creating the successor. Names such as `R2`, `R3`, timestamps, titles, and free text never imply lineage.

LE BI lists only authoritative `closure_state=open` Runs as active. Superseded, abandoned, and closed Runs remain in history. It displays the Router-controlled expected actor/action and last confirmed transition; an old start event is never labelled current work. Counts come from accepted results, not messages.

## Windows headless rule

Router runner, detached transport job, Codex App Server, DSH, OCRV, and similar child processes share one Windows no-window subprocess policy. Tests inspect launch flags; no test opens a real window.

## Explicit exclusions

- No Temporal, service mesh, message broker, extra database, MCP server, hidden Agent, or replacement Worker/Checker.
- No Router product judgment, D1/D2 authority, code modification, or evidence invention.
- No direct BI writes and no BI-derived control decisions.
- No continuous Supervisor participation and no positive-duration `wait_threads` loop.
- No lineage inference, stale-status liveness claim, or TOKEN movement before native start proof.
- No RTK/Repo Map/Headroom integration in this topology release; optional Token tools remain a later, independent optimization after control correctness.

## Compatibility

Existing 4.x Runs remain bound to their version and are never silently reinterpreted. A 5.0 Run uses schema v4, the Router identity, closed result inbox, transition ledger, and explicit binding mode from initialization. Migration of an active 4.x Run requires a new 5.0 Run identity or an Owner-approved explicit migration record.

## Acceptance

1. Four-role authority is mechanically enforced; Supervisor-hosted binding shares a task but not credentials or authorship.
2. Worker/Checker/Supervisor results cannot move TOKEN or projected state directly.
3. The complete PASS, FAIL/rework, next-CELL, D2, BLOCKED, invalid-result, timeout, and restart paths apply the closed transition table exactly once.
4. TOKEN commits only after matching native start proof; prepared/failed/replayed transitions do not duplicate work.
5. Router never authors D0/D1/D2 or chooses among ambiguous routes; those cases wake Supervisor.
6. A stopped target turn is distinguished from legal pause/block/wait states, without `wait_threads` or chat polling.
7. Explicit successor creation leaves one active successor and archives its predecessor; unrelated Runs remain visible.
8. LE BI shows authoritative state without stale “working” claims or duplicate active successor history.
9. All relevant child processes are headless on Windows.
10. Role Eval variants, normal/optimized Python, Rust, BI, repository, schema, migration, manifest/hash, and diff gates pass.
