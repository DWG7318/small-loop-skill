# SLK 4.2.0 Minimal Runtime Guard Design

**Date:** 2026-09-22
**Status:** Owner-approved design, ready for TDD implementation

## Purpose

SLK 4.2.0 reduces cross-project interpretation drift and closes the concrete continuity and Run-lifecycle failures observed in LCaS without changing the Supervisor, Checker, Worker, CELL, D0, D1, D2, rework, TOKEN, or communication topology.

This release does not add Temporal, a daemon, a scheduler, an MCP server, a role, or a second state store. It reuses the existing SQLite state core, detached `slk-transport send` job, and read-only LE BI.

## Decisions

### 1. Structured role Eval

One versioned JSON case pack defines closed, role-scoped decisions for Supervisor, Checker, and Worker. A standard-library validator accepts only the exact case set and expected choices for the requested role. Project names, paths, Run IDs, field order, and harmless whitespace cannot change the result.

The Eval covers the high-error rules: Supervisor does not wait online or replace Checker at D1; Checker owns dispatch, D1, and rework; Worker owns current-CELL implementation and D0; delivery is not acceptance; D1 is not D2; stale status is not activity; exact endpoints are required; independent Runs are distinct from successors; optional efficiency tools fail open to native commands; compressed output cannot replace decisive evidence.

Supervisor passes the Eval before takeover. Checker and Worker pass their role section before first assignment. The Eval is a readiness gate, not a new role or continuing conversation.

### 2. Atomic successor Run lifecycle

Independent open Runs may continue to share one project. A successor correction is different and must be explicit.

The state schema records one predecessor-successor edge. A new authenticated `init-successor` operation verifies the predecessor's active Supervisor identity, same project, open predecessor, absent successor collision, and one-successor rule. In one immediate transaction it creates the successor, records the lineage edge and `RUN_SUPERSEDED` fact, and archives the predecessor. The operation does not require the Supervisor to hold the current CELL TOKEN because lifecycle control is not CELL execution authority.

The legacy explicit `RUN_SUPERSEDED` write remains available only for an already-existing same-project successor and creates the same unique lineage edge. It rejects self-links, missing successors, closed or already-linked predecessors, cross-project successors, and cycles.

No existing Run is linked from names, timestamps, `R2/R3` suffixes, or free-form boundary JSON. Historical LCaS correction is a separate Owner-authorized data operation after the new core is accepted.

### 3. Boundary continuity without a workflow platform

The existing detached `slk-transport send` job remains the only boundary executor. On Codex targets, `CODEX_THREAD_BUSY` is treated as a transient condition inside the existing startup deadline. The job re-reads the exact frozen thread until it is idle or the deadline expires, then starts exactly one turn. A fake clock/sleeper proves retry timing without real sleeps.

All other identity, endpoint, start-proof, and immutable-message rules remain fail closed. A deadline expiry produces one terminal failure; it never guesses another task, creates another role, or loops forever. The method continues to say that TOKEN ownership and old `WORK_STARTED` facts do not prove current execution.

LE BI changes the misleading `Worker 工作中`/equivalent language to a factual “started; later execution unconfirmed” form whenever only durable start evidence exists.

### 4. Windows headless execution

The detached transport job, Codex App Server, DSH, and OCRV child processes use one shared Windows-only no-window subprocess policy. Non-Windows behavior is unchanged. Tests inspect launch arguments; they do not open real windows.

### 5. Minimal Token/context tooling

SLK keeps only two optional tools:

- RTK for low-noise exploratory test, build, search, and Git output. It is called explicitly, never through automatic hooks. Final acceptance and any decisive failure evidence use native commands or retrieved raw output.
- Probe CLI direct mode for token-bounded local code location before precise reads. Its Agent, MCP, edit, delegation, LSP daemon, and indexing modes are outside SLK.

RTK and Probe are optional machine-level capabilities. Missing, failing, truncated, or doubtful output falls back to native commands without blocking the Run. Aider Repo Map is not adopted because it brings the Aider application and continuously injected maps; Atlas is not adopted because the standalone implementation is newer and absent from the accepted Windows baseline; Ponytail is removed from canonical guidance; Headroom remains deferred.

## LE BI lineage presentation

Run summaries expose the explicit predecessor identity. BI shows only `open` Runs as active, preserves closed/superseded Runs in the archive, and labels predecessor history on expansion. If an explicit lineage is inconsistent, BI shows an integrity warning instead of silently hiding a row. It never selects a head by creation time alone.

The project total remains a history count. Active Run count is derived from authoritative closure state and shown separately where a count is displayed.

## Negative rules

- Do not create a successor with ordinary `init-run` and leave the predecessor open.
- Do not require the current CELL TOKEN for Supervisor-owned lifecycle closure.
- Do not infer a lineage from names, suffixes, timestamps, or free text.
- Do not report a stale start fact as current work.
- Do not use positive-duration `wait_threads` to implement continuity.
- Do not create a daemon, heartbeat role, substitute Agent, or hidden Agent.
- Do not enable RTK hooks, Probe Agent/MCP/edit/delegation, or automatic model changes.
- Do not let compressed output replace core diff, exact failure text, D0/D1/D2 criteria, or final evidence.

## Compatibility and migration

Schema migration adds lineage storage and backfills only existing authoritative `superseded_by_run_id` relationships. All unrelated open Runs stay independent and open. Existing 4.1.1 endpoints keep their field shape; `startup_timeout_seconds` is clarified as the total native-start deadline.

The four uncommitted BI edits in the original `D:\SLK` checkout are user-owned. Implementation occurs in an isolated worktree and incorporates their intended version-label and post-D1 status corrections without modifying the original checkout.

## Acceptance

1. The same role Eval decisions pass under at least three project/Run/path identities; missing, duplicate, stale, wrong-role, wrong-choice, case, whitespace, and extra-field variants fail in normal and optimized Python.
2. Independent Runs in one project remain legal; successor creation atomically leaves one open head and one archived predecessor.
3. Cross-project, missing, self, cycle, duplicate-successor, non-Supervisor, and closed-predecessor lineage attempts fail closed.
4. A busy Codex target becomes idle within the startup deadline and starts exactly once; permanent busy ends once with a stable failure; no replacement task is created.
5. OCRV, DSH, Codex, and detached job launches are headless on Windows.
6. BI never calls an old start fact current work and does not hide unrelated independent Runs.
7. RTK and Probe presence passes; absence and command failure select native fallback; final evidence remains uncompressed.
8. Rust, Python, BI, repository, schema migration, manifest/hash, version, diff, and `python -O` gates pass.
