# SLK 4.2.3 Runtime Consistency Hardening Design

Date: 2026-09-22
Status: Owner-authorized implementation baseline

## Problem

SLK 4.2.2 proved that the three-role Loop, D1 rework route, direct inactive-Supervisor wake, explicit method adoption, and one foreground Overwatcher are viable. Its first field Run also exposed protocol gaps that prompts cannot close:

- DSH and OCRV may write `started.json` only after their blocking process returns;
- an inactive Supervisor and an active writer are different native states but use one delivery path;
- TOKEN, latest event, message identity, Overwatcher cycle, and BI can describe different logical revisions;
- a writable worktree can still have an unwritable shared Git common directory;
- long command-line envelopes and unconstrained DSH instance IDs make task identity fragile;
- Overwatcher cadence, native liveness, instruction scope, incident history, and evidence integrity are not independently represented;
- a nonterminal Run can retain an `active/observing` projection after the exact foreground turn ended;
- local installation can update Skills/binaries without updating docs and schemas as one verified unit.

SLK 4.2.3 hardens those existing boundaries. It does not add a role, background runtime, scheduler, heartbeat, BoM, second Checker, or new public workflow layer.

## Inputs and authority

The authoritative maintenance input is `docs/maintenance/2026-09-22-slk-next-upgrade-guide-review.md` at commit `a05c64ecdf3e8fe1dcf75a074ae68fc2f2b49f7b`. The inactive-Supervisor diagnostic report is registered there with SHA-256 `a72d4bf4f8563c709f29c9ef706c0f4bdbfff99a06b2773107172b33e4bf864d`.

Owner decisions applied here:

1. BoM is disabled and is not a 4.2.3 candidate.
2. The current `Checker → Supervisor structured rework directive → same Worker → Checker` route remains authoritative after valid D1 FAIL.
3. R3B is not an implementation sandbox. It may explicitly adopt 4.2.3 only after the global installation is verified, and its Supervisor—not this maintenance Run—decides when to start CELL03.
4. A real CELL03 D1 FAIL may exercise the installed inactive-Supervisor wake path; no fake product failure may be manufactured.

## Considered approaches

### A. Extend the existing state and transport boundaries — selected

Add closed transport evidence, one atomic delivery-start transaction, revisioned read snapshots, bounded workspace/task preflight, and explicit Overwatcher status records to the existing Python and Rust components. Add a staged local package installer with rollback. This is the smallest approach that can mechanically reject the observed failures.

### B. Add a persistent coordinator service — rejected

A service could centralize polling and recovery, but it would become a new runtime, scheduler, and likely a fourth control authority. It would duplicate the existing state core and violate the lightweight/non-daemon boundary.

### C. Strengthen Skills and prompts only — rejected

Documentation can explain the intended behavior but cannot make a late start receipt early, atomically bind TOKEN to a started message, validate Git common-dir access, prove a foreground turn remains active, or roll back a mixed installation.

## Architecture

### 1. Transport start and task identity

The existing endpoint and envelope identities remain closed. 4.2.3 adds a closed immutable task-file contract rather than expanding prompts:

- the adapter writes `slk.transport-task/v1` atomically;
- the task binds the exact endpoint/envelope, result contract/path, task SHA-256, Run/CELL/attempt, and evidence root;
- DSH receives only a short task-file path and hash instruction;
- OCRV receives a request file containing an adapter-generated review invocation ID and must echo it in the terminal result;
- missing, changed, unreadable, or hash-mismatched task files fail closed;
- old Run files in the same directory are never searched or selected.

DSH moves from blocking `subprocess.run` to a bounded `Popen` loop. For a resumed Worker, the already-bound session ID and live process establish native start. For first activation, exactly one new session file must appear while the process is still running. The adapter then writes `started.json` immediately and continues waiting for the terminal Worker result.

OCRV also uses a bounded `Popen` loop. A fresh adapter-generated `review_invocation_id`, successful native process creation, and the closed request file establish start; `started.json` is written before the review result. The terminal result must echo that invocation ID and add the OCRV session/model/verdict identity. Process exit or terminal output may never backfill a missing start receipt.

The transport CLI continues returning as soon as start or terminal evidence becomes visible. Tests use injected clocks and delayed fake processes; they do not sleep for production-scale intervals.

### 2. Supervisor state split and active-writer recovery

Codex delivery first reads the exact target thread:

- `idle` or `notLoaded`: use the existing exact-thread `turn/start` path;
- `active`: do not wait for idle and do not replay the original envelope;
- terminal, missing, wrong thread, or unsupported state: fail closed.

For an active writer, only `D1_FAILURE_ESCALATION` may use active-writer recovery. The adapter reads the exact active turn, creates a new logical message UUID, and uses native `turn/steer` with `expectedTurnId`. It writes an immutable `slk.transport-active-writer-recovery/v1` receipt binding:

- original failed message ID;
- new recovery message ID;
- exact Run/GO/CELL/round and payload SHA-256;
- exact thread and active turn IDs;
- original failure evidence;
- steer acceptance and timestamps.

The original attempt remains `failed` and immutable. The recovery is a new message, executes at most once, and cannot change receiver, route, payload, TOKEN scope, or endpoint version. A non-steerable/mismatched turn or second recovery returns `SUPERVISOR_DECISION_REQUIRED`.

The already-proven inactive/notLoaded path remains direct and does not detour through recovery.

### 3. Atomic delivery start and runtime snapshot revision

SQLite schema v7 adds:

- `runs.current_runtime_revision`;
- append-only `transport_start_receipts`;
- append-only `run_runtime_snapshots`;
- Overwatcher liveness, incident, and transition records described below.

The new `slk-state commit-delivery-start` operation replaces separate handoff for Runs whose effective contract is 4.2.3. It accepts the current sender credential, exact token transition, the immutable `started.json` or active-writer recovery receipt identity, and the corresponding endpoint/envelope hashes. In one immediate transaction it:

1. authenticates the current TOKEN owner and route;
2. verifies the registered start evidence exists and still matches its SHA-256;
3. records the transport-start receipt;
4. appends the next TOKEN event;
5. appends a `TRANSPORT_STARTED` work event;
6. increments `current_runtime_revision`;
7. writes one materialized runtime snapshot containing that revision, TOKEN, latest event, message, plan, CELL, method version, and Overwatcher binding/status identity.

Any mismatch rolls back every step. Legacy `handoff` remains available to pre-4.2.3 Runs but is rejected after a Run explicitly adopts 4.2.3, preventing bypass.

`slk-bi-query`, export, and Overwatcher cycles consume one committed runtime snapshot instead of independently choosing the newest rows from several tables. Readers may see the old or new revision, never a mixed one.

Method adoption adds the explicit `4.2.2 → 4.2.3` transition. It preserves origin version, TOKEN, roles, CELL/D1 history, and evidence. An open Run with an existing Overwatcher must declare either exact active-binding preservation or `CONTINUITY_RECOVERY_REQUIRED`; adoption never silently repairs or rebinds it, and dispatch remains closed until continuity is proven or an authorized replacement is recorded.

### 4. Worker workspace and instance preflight

Before DSH starts, the adapter performs a closed Git preflight:

- the workspace must be a Git worktree with an exact top-level path;
- the worktree path must be writable;
- the resolved Git common directory must exist and be writable;
- a standalone clone is the default and passes when its common directory is inside the workspace;
- a linked worktree passes only when its shared common directory is explicitly reachable and writable;
- failure occurs before model/process start and creates no Worker session.

The shared instance-ID helper produces one deterministic Run-scoped DSH identifier no longer than 64 characters. Short canonical IDs remain readable; long IDs use a bounded prefix plus a hash suffix. Endpoint validation and every producer use the same helper. Alternate, overlong, cross-Run, or collision-prone values are rejected before launch.

### 5. Overwatcher continuity

The public contract remains one optional Overwatcher per Run, with one binding, one Session, and one foreground active turn across every CELL. 4.2.3 makes its facts explicit:

- binding revision and canonical control task identity;
- observed runtime snapshot revision;
- scheduled/start/completed times, lateness, grace, and cadence health;
- exact native session/turn status, separate from cadence health;
- stable incidents with `OPEN → ACKNOWLEDGED → RESOLVED` transitions;
- closed evidence references containing path and SHA-256, verified before cycle commit;
- lightweight optional cost counters that never influence routing or model choice.

Only messages from the frozen canonical control task after the binding revision are eligible as current instructions. Historical source tasks remain evidence only.

A closed native-status receipt may be recorded by the bound Overwatcher or an authorized current technical role after reading exact native evidence. If the Run is open and the exact turn is completed, missing, or mismatched, the state core records `OVERWATCHER_CONTINUITY_VIOLATION`, changes the current binding projection to violation, and blocks `CELL_DISPATCHED`, rework dispatch, and delivery-start commit. Cadence lateness alone produces `CADENCE_LATE`; it never becomes inactive while exact native evidence says `inProgress`.

The CLI adds `wait-for-change`: one foreground call waits for a later runtime revision or the bound 180–300 second deadline, then returns. It creates no task, heartbeat, cron entry, daemon, process loop outside the caller, or second Agent.

### 6. Final cycle, close, and authorized replacement

Normal CELL boundaries never suspend, release, close, or rebind the Overwatcher.

After `RUN_CLOSED` or `RUN_ABANDONED`, closure requires:

1. a final cycle over the same current runtime revision;
2. a lifecycle transition receipt citing that cycle and its verified evidence;
3. credential revocation and archived projection;
4. only then may the native foreground turn end and the Session be archived.

A planned authorized replacement while the Run remains open follows the same final-cycle-first order and requires explicit Supervisor authorization evidence. The replacement gets the next binding revision and cannot overlap the old binding.

An unplanned dead turn cannot fabricate a final cycle. It records an immutable continuity incident and incomplete shutdown. Recovery requires an explicitly authorized replacement receipt that preserves the gap; it never rewrites the old binding as cleanly closed.

### 7. Evidence and incident integrity

Every Overwatcher evidence reference is verified for existence, file type, readable bytes, and SHA-256 before insertion. A bad path/hash makes the cycle `INCOMPLETE_EVIDENCE_REF` and prevents a complete-cycle claim.

Incident IDs are stable. Current projections contain only unresolved incidents; resolved items remain in append-only history with their resolution revision. A cycle cannot silently drop an open incident or repeat an already-applied transition under new text.

### 8. Versioned package and local installation

All repository version surfaces move together to 4.2.3. A local package builder stages:

- 15 Skills;
- `slk-state.exe`, `slk-bi-query.exe`, `slk-cargo.exe`, `slk-bi-desktop.exe`, and `slk-transport.pyz`;
- state, BI, transport, and runtime docs;
- closed JSON contract schemas and SQLite schema identity;
- README/MIGRATION/CHANGELOG/VERSION and an install manifest with SHA-256 for every packaged file.

The local installer takes an explicit package root and Codex home. It verifies the complete package before mutation, backs up every managed destination, stages all replacements, installs them, and runs installed-path identity checks. If any copy or verification fails, it restores the full previous managed set and verifies rollback. A partially mixed 4.2.2/4.2.3 installation is never reported as success.

The installer does not migrate or write any product Run. Database schema migration remains an explicit `slk-state configure` action against a chosen data root and continues making a verified backup first.

## Error handling

- All new JSON types deny unknown fields and use closed enums.
- Start evidence cannot be inferred from terminal output.
- A new recovery message is allowed only for an exact active-writer D1 escalation and only once.
- A missing or stale runtime revision, start receipt, TOKEN owner, endpoint, task hash, evidence hash, active turn, or incident transition aborts before state mutation.
- A nonterminal Overwatcher continuity violation blocks new dispatch; it is not normalized to suspended or released.
- Installation failures roll back the whole managed set and leave a failed-install report outside the active install tree.

## Validation strategy

TDD covers the maintenance record's 21 normalized negative cases plus these integration paths:

1. delayed DSH/OCRV terminals prove `started.json` exists while the process still runs;
2. inactive/notLoaded Supervisor follows direct `turn/start` and produces one turn;
3. active writer uses one new `turn/steer` message, keeps the old attempt failed, and rejects changed or duplicate recovery;
4. a temporary state database atomically commits started receipt, Checker→Supervisor TOKEN handoff, `TRANSPORT_STARTED`, and one runtime revision;
5. concurrent readers see only complete old/new snapshots;
6. standalone clone passes while an unwritable shared Git common directory fails before process start;
7. task-file hash drift, old-file distraction, and instance IDs over64 characters fail closed;
8. cadence late plus native `inProgress` remains live; completed/missing turn creates a continuity violation and blocks dispatch;
9. instruction-scope, incident-lifecycle, and evidence-ref negative cases remain closed;
10. final-cycle failure prevents clean close; terminal close and planned replacement require the exact final revision;
11. BoM references in runtime contracts, positive Evals, or routes are rejected;
12. ordinary and `python -O` validation produce the same closed decisions;
13. a disposable standalone repository, temporary state root, fake DSH/OCRV, and fake Codex App Server complete one minimal serial sandbox Run without touching LCaS;
14. a disposable Codex home proves package install, installed versions/hashes/CLI smoke, deliberate failure rollback, and no mixed tree.

Full repository, Rust, Python, BI, packaging, install, mirror/version, sensitive-data, and diff gates run before installation. Installed-path verification runs again after installation.

## Compatibility and migration

- Existing databases migrate from schema v6 to v7 only through the normal backed-up configure path.
- Existing 4.2.2 Runs remain valid under 4.2.2 semantics until they explicitly adopt 4.2.3.
- 4.2.3 Runs must use `commit-delivery-start`; legacy handoff cannot bypass the atomic receipt/revision gate.
- Existing evidence and 4.2.2 history remain immutable.
- R3B adoption may record `CONTINUITY_RECOVERY_REQUIRED`; this is a truthful migration state, not an automatic repair.

## Non-goals

4.2.3 does not modify LCaS, R3B, or CELL03; create a fake D1 FAIL; add BoM; add a Router; replace the direct Supervisor/Checker/Worker topology; create a resident service, scheduler, heartbeat, daemon, background Agent, or second Overwatcher; make BI writable; let Overwatcher own TOKEN or engineering verdicts; automatically upgrade DeepSeek V4 Flash; or push/tag/publish the repository.
