## 目标和范围

Owner 要求取消 SLK 对 DSH、OCRV、Codex 输出结果的一切审核和放行门槛，并评估、精简依赖这些门槛的其他机制。不是只修 20000 字符错误，也不是取消 Worker 的 D0、Checker 的 D1 或 Supervisor 的 D2。

原则：Agent 输出先保存、交给接收角色；SLK 不以正文格式、长度、finding 级别、证据完整性或工程结论作为投递前提。工程是否完成、是否通过、如何返工，由有职责的 Agent 决定。

## 已核对的实际问题

1. `integrations/ocrv/slk_checker_adapter.py::_classify` 按 finding 严重度生成 PASS / FAIL / INCOMPLETE；MEDIUM 及以上直接 FAIL，完整且零 finding 或只有低级别 finding 则 PASS。该函数还检查 coverage、模型、工具失败和输出结构。这不是单纯搬运 OCRV 已经明确作出的 D1 决定。
2. 本次 CELL05-A 第二轮原始 `ocrv-review.json` 的顶层没有 D1 `verdict`；其 message 是审查完成及 finding 数量。正式 `ocrv-result.json` 的 FAIL 来自上述适配逻辑。有效 finding 是否成立与正式 D1 判定由谁作出，是两个问题；此前把二者统称为 Checker 结论不准确。
3. `src/slk_transport/partial_review.py::_complete_verdict` 还有同类按严重度合成结论的路径，只改主适配函数会留下旁路。
4. DSH `_read_result` 要求输出采用严格封闭字段集；结果格式不符会变成 `DSH_RESULT_INVALID`，另起补交、恢复与续接链。
5. Codex `RoleHost._supervisor_result` 检查固定字段、可用证据、原 findings 逐字段相等及固定管理动作；第二次 FAIL 还由代码强制拦下普通返工。指引与工程判断被编码为宿主放行条件。
6. `RoleHost`、`worker_completion`、`checker_completion`、`checker_escalation` 依赖上述结构和自动结论，再决定状态写入、交接与下一动作。
7. Temporal `request_delivery` 的 runtime guard 会拦截投递；当前实现没有先区分“派下一 CELL”和“交出已经产生的结果”，因此保障异常可能扣住结果或异常报告。
8. Codex Desktop 共用发送路径有发送前读取、发送后回读及恢复证明链。本次长材料修正已部署，但原操作确认仍受 attempt 与恢复证据识别问题影响。正文读取、实际投递和责任确认耦合，不应成为审阅输出的另一个入口。

## 两种必须区分的结果

- **通信事实**：谁实际产生了文件、发给谁、是否投递、是否收到、是否真实启动。Tool 记录这些客观事实。
- **工程判断**：候选是否正确、D0 是否足够、D1 是否通过、是否返工/拆分、D2 是否闭合。对应 Agent 作出判断，Tool 不重新裁决。

通信成功不能写成工程 PASS；工程 FAIL、报告缺项或无法解析也不能写成“报告不能交付”。Agent 尚未明确下结论时，先交报告，不猜 PASS、FAIL 或 INCOMPLETE。

## 关联影响及精简处置

| 机制 | 当前耦合与风险 | 处置方向 |
| --- | --- | --- |
| DSH 结果合同 | 少字段、多字段、嵌套差异会扣住已经产生的结果 | 删除正文封闭字段集放行；原结果、日志和文件位置照常交给 Checker，候选/D0 是否充分由 Checker 判断 |
| OCRV 自动分类 | 代码按严重度、覆盖率和退出状态生成工程裁决 | 删除主路径及 partial/context/recovery 旁路的自动裁决；由原 Checker 明确给出 D1 判断，不另设审批角色 |
| Codex 决策合同 | 固定动作、字段完全一致、证据文件形态成为交付前提 | 移除内容放行和固定动作枚举门槛；Supervisor 决定可被原样交出，工程范围约束通过角色指引承担 |
| 结果格式补交恢复 | 为满足宿主格式重新唤醒 Worker、制造恢复链 | 删除新结果对这套补交链的依赖；历史材料只读保留，不继续要求 Agent 为 SLK 格式重新工作 |
| RoleHost 自动后缀 | “结果通过宿主检查”才允许交给下一角色 | 改为结果投递与角色明确动作分离；不让输出不合模板阻断结果交付 |
| FAIL / PASS 路由 | 依赖代码自动生成的 D1 状态 | 只执行对应角色明确的下一动作；缺少角色结论时交给原责任角色处理，不自动前进、返工或改判 |
| 第二次 FAIL 强制拆分 | 代码将角色工作方法变成不可绕过的门禁 | 拆分与调查要求保留在 Skill，移除宿主针对输出的硬拦截；不取消 Owner 要求的认真调查 |
| Temporal guard / ACK | 保障异常与内部回执阻挡已生成的结果 | 结果和异常报告不得被工程派工门禁扣住；确认失败作为独立通信异常交给 Supervisor，不反复要求重新审查或生成报告 |
| TOKEN / 状态记录 | 把输出合格与接收者接手捆绑 | 保留身份、权限、原子更新和历史；状态仅记录 Agent 明确动作，不用报告正文审查决定能否转交报告 |
| OW | 依赖预审状态误判正常/异常，或等状态才能上报 | 检查真实活动和未接手结果，报告事实；不增加输出审核，不代替工程角色裁决 |
| BI / 导出 | 可能把收到报告、完成审查和通过验收显示为同一件事 | 显示真实投递与角色判断，不能显示“收到=PASS”，也不能因报告不合格式隐藏已存在结果 |
| 主/子 Skill、文档、测试 | 仍要求代码按级别判 FAIL、输出严格格式或恢复后缀 | 同步删除这些要求；测试改验结果可交付、结论不被合成或改写，不保留旧门槛的回归断言 |
| 安装包与现有端点 | 源码、已安装工具、旧 Host 可能行为不同 | 改完独立验证、统一部署后再恢复；不只改提示词，不冒称停着的旧 Host 已采用新行为 |

## 保留什么，不扩大成新的审核层

- 保留基础通信信封的发送者、接收者、Run/消息身份及授权校验；这是防发错对象，不要求 Agent 正文重复满足同一套严格字段。
- 保留原始输出、不可变历史和防重复投递；重试不能制造重复施工。
- 保留文件字节完整性和真实收发记录；这些检查只约束工具自己的传输材料，不裁决工程内容。
- 保留 D0 / D1 / D2 角色职责与 Owner 工程范围。SLK 不再用额外程序审核角色结论。
- Agent 本地开工前轻量预检不属于输出预审，可用于合理安排工作；不得借此重新加入报告放行、统一字数或统一预算门槛。
- 无输出、进程异常或目标不可达时，交出已有日志和事实；不得编造报告、假装已送达或默认通过。

## 重要迁移约束

1. 不能只把 `_classify` 改成默认 PASS，或全部改成 INCOMPLETE；两者仍是代码替角色下结论。
2. 当前 OCRV 接口主要提供 findings，原生 JSON 未在本例中表达正式 D1 verdict。删除自动分类时，必须让**原 Checker**承担并明确表达最终 D1 判断。不能把判断转交给 SLK，也不能由 Codex 冒充 Checker。优先使用原 Checker 会话和现有能力，不新增审查角色或恢复系统。
3. 角色输出形式不被审核，不等于 Tool 可以从含混自然语言猜测有副作用的指令；工程动作通过对应角色明确调用既有标准入口。未明示动作时报告仍交付，接收角色继续履责。
4. 旧 FAIL 和恢复记录保持原样。补充注明历史判定来源即可，不能重写历史为 PASS，也不自动重跑已完成审查。
5. 通信失败仍可能发生，不能承诺任何故障下都送达；必须明确区分“实际投递失败”和“宿主嫌内容不合格”。后者不再存在。

## 验收：以真实交付行为为准

- 长报告不截断，结果长度不成为放行门槛。
- DSH 输出多字段、少字段、嵌套结构或非 JSON 时，已有输出仍交给 Checker，不启动格式补交施工。
- OCRV 输出 zero / low / medium / unknown findings 时，SLK 不自行生成或修改 D1 结论；有无明确结论均不扣住报告。
- OCRV 部分完成、工具失败或进程非零退出时，原报告和实际故障照常交出，不伪造完整审查。
- Codex 输出非固定模板、证据引用不完整或提出不同的范围内处理动作时，结果仍被交付，由相应角色处理，不因模板失败停留。
- runtime guard 或回执维护异常不得扣住已经产生的结果；报告送达与状态提交分别记录，不把后者失败误称报告不存在。
- 正常投递、精确恢复、不同工程尝试编号使用相同瘦身路径；已有真实送达不重复发送。
- 错 Run、错接收者、未授权状态更新、重复消息与内容漂移仍不能被伪装成合法新工作。
- 完成源码、相关文档/Skill/测试及已安装工具的一致验证后，才允许声称“已移除并可用于施工”。本文件不构成该证明。
