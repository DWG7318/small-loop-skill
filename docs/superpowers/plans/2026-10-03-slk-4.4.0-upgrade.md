## 1. 准备与登记

- 用一个准备子 Skill 整合现有角色建立、登记、环境/工具预检、必要通讯演练、纠正及成员替换，不重复建设相同能力。
- Supervisor 必须由 Owner 确认。Agent 实例与 Session 分开登记，绑定设备、运行平台、角色、模型/reasoning、真实通信端点、投递及状态查询适配器、成功信号和版本；禁止凭标题猜身份。
- 按统一 SLK 标准准备必需 Skill、工具、Agent、TOKEN、BI 与设备环境；Supervisor 可补充项目所需项。可选效率工具的准备与是否启用分别记录。
- 准备阶段必须打开 BI，检查工具更新需求；本轮包括 OCRV、DSH 升级和兼容性验证，Checker 暂保留 Qwen3.8-Max。
- Supervisor 使用 Owner 选定的 Sol 或同级模型；OW 的 Luna 或同级模型及 reasoning 由 Owner 决定，不写死旧型号或静默切换。
- 成员、Session、端点或有关运行绑定替换时保留旧登记并产生新版本，重新验证受影响通路。纠正后的配置和调用方式绑定版本，禁止工作中漂回旧路径。
- BI 只读团队登记。OCRV、DSH 和辅助进程使用 headless；正常可视化 BI 窗口保持可见。

## 2. 已确定的工程通讯基线

- 初始计划交接和必要调整使用 Supervisor 与 Checker 的既有通路。
- 日常施工：Checker → Worker → Checker；D1 PASS 后由 Checker 派发下一 CELL，全部结束后交 Supervisor 做 D2。
- D1 FAIL：Checker → Supervisor → 同一 Worker → Checker。Supervisor 发送结构化返工指引，Checker 保持独立 D1 权威；Supervisor → Worker 不是一般派工通路。
- 同一 CELL 连续两次正式 D1 FAIL 后，Supervisor 必须升级调查：对照两轮 findings、候选 diff、实际步骤及复现/回归证据，检查根因、范围、上下文、工具和环境，并形成更明确的实验与修复指引；不能只重复普通返工建议。
- INCOMPLETE、通讯/工具故障和重复回执不计为正式失败；保留既有第三次失败后的重新规划闸门。Supervisor 不替 Worker 施工，不覆盖 D1。
- 原责任成员的标准 CLI 入口完成交接；复用现有 transport、证据和认证机制，不新增统一 API 服务。真实发送者与接收者必须能沿必要路径准确投递和真实启动，不能以 OW、方法负责人或演练脚本代发的成功替代。
- 分开确认接收、原生启动和工程结果；未证明接收者真实启动时，原发送者保留责任与 TOKEN。通讯故障不能伪造为 D1 FAIL，投递成功不能伪造为 D1 PASS。
- 工具版本验收覆盖完整正常链、返工链及故障；每个 Run 的准备阶段进行轻量绑定/通路验证，完整身份未变时复用有效结果，变化后只复测受影响部分。

## 3. Temporal：服务共用，各 Run 独立管理

- Temporal 为必选运行保障，使用本地服务和 headless 执行进程。基础服务与执行程序可被多个同版本 Run 共用，不为每个 Run 重复部署服务、数据库和端口。
- 原地升级现有“启动 SLK”和“进行 SLK”两个模板。每个 SLK Run 拥有独立的一对工作流、业务身份、交接记录、计时器和恢复状态；项目填写参数，不重新编写工作流。
- 工作流 ID 由稳定的 SLK Run 身份生成；Temporal 自身执行 Run ID 与 SLK 业务 Run ID 分开记录，不能混用。
- 各工作流独立计算时间：Run A 的开始、交接、恢复、结束不重置 Run B 的时间，也不能消费、取消或覆盖 B 的操作与证据。
- 成员停留计时绑定当前 Run/CELL/责任节点及真实交接时间。重复消息、重试或自由文本状态不能刷新计时；有效交接收尾旧节点并为新节点独立起算。
- 单个 Run 的工作流关闭仅取消自己的计时与待处理操作；其余 Run 继续运行。单个 Run 的 Supervisor 不得顺手关闭共用服务；没有其他使用者后才可正常关停服务和执行进程。
- Temporal 保存运行保障事实及现有权威证据引用，不产生第二套工程真相，不决定 D0/D1/D2、不自行移动 TOKEN、修改 BI、创建/替换角色或选择模型。

## 4. 时间与观察责任

| 事项 | 固定时间 | 责任及动作 |
|---|---|---|
| OW 主动巡查 | 默认每 10 分钟 | OW 在自身持续 active 的 Session 内主动核实、记录、报告并继续观察；不是 Temporal 定时唤醒。 |
| 独立核查 OW | 每 20 分钟 | Temporal 触发原生活动与巡查证据核查，异常交相关 Run 登记的 Supervisor。 |
| 工作停留在同一成员 | 超过 30 分钟 | Temporal 经现有投递适配器直接通知对应 Supervisor 排查，不经过 OW 中转。 |

- 不保留 5/7 分钟巡查选项或 45 分钟门槛；成员停留提醒不额外判断是否有实质进展，长测试是否正常由 Supervisor 确认。
- 启动 ACK/投递失败使用既有独立、受限的通讯超时，不能等成员停留提醒再处理。
- 同一个 OW 服务多个 Run 时统一 10 分钟巡查间隔，严格区分各 Run 的事实、成员和 Supervisor 端点。
- 共享 OW 的 20 分钟核查按 OW 实例/Session 与核查周期形成确定性身份，重复触发复用同一核查事实；按受影响 Run 向其 Supervisor 报告并去重，不能错投或因多个 Run 重复激活同一处理。
- 单个 Run 结束不能取消其他 Run 对共享 OW 的核查需求，也不能重置其正常巡查节拍。

## 5. OW、恢复和停止

- 每个 Run 必须登记且只能绑定一个有效 OW；由 Supervisor 创建或指定真实 Agent Session，允许服务多个 Run，不能依靠 heartbeat 或定时任务冒充全程主动运行。
- OW 对照 BI、TOKEN、消息及原生状态证据核实真实性，记录自己的观察；矛盾、无法判断及疑似异常均向唯一登记的对应 Supervisor 上报，UNKNOWN 不能写成正常。
- OW 正常巡查或异常成功上报后均继续观察。它不写 BI/TOKEN/工程结果、不做 D1、不成为正式交接中继，也不承担工程修复或提出返工方案。
- 机械恢复优先，Supervisor 决定方式并可同时观察、指导和记录；同一恢复操作共用确定性身份，复用现有受限重试/恢复，禁止重复施工、重复验收或争夺同一原生 writer。
- Temporal Activity 完成不证明 Agent 原生启动，工作流重放不能成为重新施工或重跑 D1 的理由；明确控制副作用重试，不沿用无界默认策略。
- Temporal 或 OW 失效时保留当前候选与证据，禁止派发下一 CELL，由 Supervisor 组织修复。Temporal 自身不可用时，由既有派发入口的可用性检查和原通讯路径报告，不依赖失效服务自报。
- 只有已登记的 Supervisor 可以正式叫停 OW。OW 不因正常、报警已送或自认 Run 完成而退出；宿主/平台退出 Hook 经登记适配器唤醒对应 Supervisor，即使 Supervisor 主动叫停也须二次确认实际停止和合法性。20 分钟独立核查覆盖 Hook 缺失。
- Run 终结由 Supervisor 确认；解除该 Run 的 OW 观察绑定，闭合本 Run 操作后正常结束其两个 Temporal 工作流。关闭工作流不以共享 OW Session 退出为前提，OW 不作为某个 Run 的子进程或随其父工作流关闭。
- OW 是否停止由 Supervisor 确认，仍服务其他 Run 时继续运行；全部绑定解除后再按确认收尾、归档。Temporal 服务/执行进程的意外退出通过宿主通知相关 Supervisor。

## 6. BI / WebBI 1.1 与安装一致性

- BI 与 WebBI 共用仓库和版本，显示 BI 版本与各 Run 的 SLK 版本；增加完整 OW Agent/模型身份、设备名称/ID 标注和点击后消失的更新绿点。
- 消息类型由事实发生处的 Agent 从封闭目录中选择并写入权威记录；状态核心机械校验类型、角色、身份和 scope。BI/WebBI 只读，不从文字、颜色、时间、投影差异或可见状态自行分类，也不生成第二套工程事实。
- 绿点只代表存在新的、可读的权威类型记录。轮询、持续时间变化、无变化 OW 巡查、重复上传和相同消息 ID 不产生绿点；打开 Run 只清除该客户端已展示版本的未读状态，历史初次导入静默建立基线。
- 各设备由现有 BI 进程每 30 秒在有新数据时独立增量上传，不新增 Node sidecar、Agent 或每 Run 同步组件；断网不影响本地 BI，恢复后按消息 ID/版本幂等补传。
- WebBI 数据范围不超过电脑 BI。Run 使用稳定 device ID + Run ID 隔离并长期保留，结束或废除只标归档；默认“进行中”，保留“已归档”，不需要“全部”或电脑切换顶层视图。
- WebBI 打开时每 30 秒刷新服务端视图；该浏览器刷新与设备上传分离且不生成消息。手机/Pad/桌面浏览器响应式体验与已确认设计一并验收，桌面 BI 的提示保持简单。
- WebBI 增加可选 ntfy 配置页：私有服务器、topic、token 或账号密码、测试消息，以及“全部新消息类型/勾选精确类型”。勾选项直接使用共享封闭类型目录；只有新入库的合法类型记录可通知，服务端保管凭证并按消息 ID 幂等发送。
- 详细底层契约见 `docs/superpowers/specs/2026-10-04-slk-4.4.0-agent-authored-bi-messages-design.md`。优先替换既有描述和调用方式；明显错误增加针对性负例。必要 Skill、合同/schema、模板、readiness、simulation、validator、测试、报告及安装文档一致同步，保持主 Skill 简洁。

7. 聚焦/全量验证、真实原生成员实测及版本/hash/镜像/安装文档一致性；正式发布按其授权门禁执行。

至少覆盖以下验收：

- Run A、B 在不同时刻交接，分别在其自身 30 分钟门槛触发准确 Supervisor 提醒；A 的重复消息、恢复或关闭不改变 B 的截止时间，过期身份不能触发新节点告警。
- 同一 OW 绑定多个 Run 的 20 分钟核查去重，告警准确关联每个受影响 Run；一个 Run 关闭后，其余 Run 的核查继续，OW 保持 active。
- 一个 Run 正常关闭自己的两工作流与计时，另一个 Run 可继续交接；共用服务不得被单 Run 收尾关掉。关闭工作流不杀共享 OW。
- 正常派工和 D1 FAIL 返工由各实际责任成员完成；普通 Supervisor → Worker、INCOMPLETE 冒充 FAIL、OW 代投正常施工和自报启动均被拒绝。
- 同一 CELL 第二次正式 D1 FAIL 触发增强调查，重复回执/工具错误不加次数，Supervisor 不接管 D1。
- OW 自行退出、异常退出、Supervisor 叫停均触发停止确认；未送达或未确认不能记录正常关闭；Hook 丢失由独立核查发现。
- Temporal/OW 失效不能派下一 CELL；恢复不重复启动、施工、D1 或移动 TOKEN。所有长间隔测试使用注入/模拟时钟，不做真实长等待。
- Agent 类型写入、错误角色、自由文本类型、重复 ID 冲突及 BI/WebBI 反向写事实均有普通与优化路径的 fail-closed 负例；轮询、时长和历史导入不产生更新消息。
- 多设备同名 Run 不冲突；WebBI/网络不可用不阻断本地 BI；ntfy 凭证不出现在浏览器响应和日志，筛选只使用正式类型目录且同一消息不重复发送。
- 辅助进程无可见控制台；BI/WebBI 数据与版本一致；安装说明不得保留与新规则冲突的可选 Temporal、OW 恢复主责、旧时间或旧通讯流。
