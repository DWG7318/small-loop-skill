## 2. 通讯验证的轻重边界

- 正常通讯责任仍是原发送者与原接收者；OW 不代发，异常补救成功不算正常通路成功。
- 发布阶段验证完整业务通路；现场核对当前身份、地址、权限、适配器及材料访问。相同安装和未变化端点的有效能力证据可以复用，身份/权限/端点变化只重查受影响部分。
- 现场可执行的短投递测试必须留有真实接收证据；静态检查、echo 或 dry-run 不能记为业务已送达。OCRV 不是任意聊天 Agent，不能为“测通”伪造 chat Session、PING 回答或 D1 结果。
- OCRV 没有廉价通用消息入口的部分，不以另一轮审查补齐形式上的七腿表格：明确现场证明范围，首次真正业务交接仍沿原入口核验 native start，再按现有合同提交 TOKEN。未启动、错地址或权限失败由 Supervisor 修复，不绕过、不重复施工。
- 因而 4.5.0 的轻量 READY 表示“组件和本 Run 绑定具备开工条件”，不声称每个本 Run 已实跑所有业务分支；原真实交接的校验没有取消。

**正式交接是最后一个任务动作：** 对每个发生工作交接的角色，先完成本阶段工作、保存结果/原始证据与必要记录、停止相关业务及子任务活动，再沿既有入口完成正式交接，成功后结束本次激活。真实接收启动、ACK 与 TOKEN 原子提交仍属于这一交接动作；不能先退出发送宿主导致交接丢失，也不能先交接再继续施工、检查、修改候选或补做其他工作。未闭合时只恢复同一交接的缺失部分，不重跑工作或重复投递。OW 异常通知不是工作权交接，不因此暂停巡查或关闭共享 Session；停止仍沿既有 Supervisor 确认规则。

- `slk-troubleshoot-preflight`：处理开工准备/重新准备中的问题，例如组件或依赖缺失、安装/版本/路径不符、角色理解或登记不完整、端点/权限/材料访问失败、BI 无法读取、Temporal/OW 尚未就绪。给出最小配置/纠正建议，修复后只复核受影响的准备条件，不重演工程链。
- `slk-troubleshoot-run`：处理正式开工后的异常，例如成员失活、通讯或交接未闭合、TOKEN/候选/运行状态矛盾、资源冲突、Temporal/OW/探针故障。先核对当前 Run/CELL/attempt 和最后可信事实，再推荐既有恢复办法，保护已完成成果、不重复施工或验收。正常 D1 FAIL 仍走既有返工/调整，不由排障 Skill 改判。

分流看当前操作：中途更换成员或升级后重新准备的缺项也可用预检排障，不按 Run 是否已存在机械区分。两份均不接管产品工程 Debug、D1 或 Supervisor 决策，共同设计原则如下：

- 短正文只说明触发条件、最小定位办法、预案索引与权限边界；故障预案按需读取，不增加开工必读项、统一审计或新的修复管理层。
- 每份预案说明现象/错误、适用版本与条件、可能原因、最直接的取证入口/命令、推荐的最小修复、修复后验证和必要回退。命令由开发阶段预先验证，并说明所需角色权限与影响范围；猜测与已证实根因分开，不按报错文字机械套用。
- 分别收录当前阶段已有的可验证经验，不要求读取另一份的全部预案；上述例子不是穷举，不设数量、排查时长或重试次数的新硬门槛。同一技术事实或修复入口可以共用按需参考，不维护两份互相漂移的操作副本。
- `slk-recover-communication` 继续保留，作为已有精确投递/交接的通讯恢复操作规程；两个排障 Skill 负责定位并推荐入口，不复制其重试、回读、ACK/TOKEN 操作。预检中的组件/地址/权限/材料访问缺项先沿团队准备入口纠正，无已有投递时不套用消息恢复；准备或施工中若符合已有精确投递的恢复前提，再按原消息与原责任角色执行。已明确的通讯故障可直接使用该恢复 Skill，不强制先经过排障；Supervisor 保留决策权，OW 不代发、不接管。BI、团队、Temporal、资源问题同样沿既有准确入口处理，不另造状态根或第二套恢复流程。
- 预案只是建议，不授予额外操作权限、不自动选择修复路线，也不把“未收录”判为不可继续。Supervisor 可按真实证据选择、调整、组合或跳过推荐办法，遇到新问题继续定位；证据不符或修复无效时反馈事实，不盲目重试或改造为旧案例。
- 修复后只复核受影响条件和实际结果，不从头重复准备、工程施工或验收；记录经验证的原因、动作、结果及适用版本，候选经验待验证后再收入维护的预案，不自动把本机偶发问题推广成全局规则。

# 第二步：逐份确认后重构 Skills

## 1. 按职责拆分，不固定 Skill 数量

Owner 确认不限制在 17 个：必要时新增、拆分或调整入口，不能留下职责混杂、要求 Agent 一次理解大段文字的大型 Skill。目标是减少一个角色在当前情境必须理解的内容，不追求更少文件，也不设统一行数、字数或 Token 硬门槛。

独立触发时机、责任和可交付结果对应独立 Skill；同一任务的参数、schema 与少见分支放按需参考。每份 Skill 应能直接指导当前动作，不能碎片化成空壳路由，也不能靠必读巨型附件或“先读全部子 Skill”掩盖阅读负担。拆分的是知识与操作指引，不增加角色、审批层、TOKEN 节点或交接次数。

| 层次 | 保留什么 | 不常驻加载什么 |
| --- | --- | --- |
| 主 Skill | 方法身份、三个主体角色职责与 OW 观察边界、真实通讯流、D0/D1/D2、TOKEN 核心边界、情境导航 | 各种恢复操作参数、schema 字段、历史版本案例 |
| 当前子 Skill | 何时使用、谁负责、输入、直接动作、交付结果、最相关禁令 | 其他角色的完整规程、与当前情境无关的故障分支 |
| 所属 references / 现有技术文档 | 条件触发的操作细节、参数示例、异常恢复、合同解释 | 不通过“为保险全部阅读”让成员整包加载 |
| 标准 Tool | 已有身份、权限、哈希、状态事务与原生事实校验 | 不把确定性校验过程再写成模型逐字段手工审计 |

技术文档继续使用现有 `docs/state`、`docs/transport`、`docs/runtime`、`docs/contracts` 权威位置；所属 `references` 只承载当前任务的条件细节，不再造一层“总管理 Skill”。优先评估团队准备与成员变更、Temporal 基本运行与故障恢复、D2 验收与验收后归档收尾等拆分边界，名称与数量由盘点确定，不预先凑数。OW 保持一个简明的巡查入口，不另造第二套 OW 规则。

## 2. 明确规则唯一归属

- 规划与 CELL 划分：`slk-plan-run`；模型选择：`slk-select-models`；独占资源：`slk-guard-resources`。
- 创建、登记、替换：团队 Skill；轻量准备、Temporal 运维及必要的恢复操作按实际边界拆分；角色说明、理解确认与纠偏沿现有团队/`slk-grill-supervisor` 职责整理，保留 Eval 资产，不新造培训或考试框架。
- 正常施工：`slk-dispatch-cell`、`slk-execute-cell`、`slk-check-cell`；正式 FAIL 的第一次返工：`slk-rework-cell`。
- 调查、进一步拆分与规划变化：`slk-adjust-run`；准确已有消息的通讯恢复：`slk-recover-communication`。
- 准备故障定位与快捷建议：`slk-troubleshoot-preflight`；施工异常定位与快捷建议：`slk-troubleshoot-run`。两份新增正文分别确认，不替代或重复 `slk-recover-communication` 等已有恢复操作。
- OW 真实性核查：`slk-overwatch-run`；各角色写自己的事实：`slk-record-run`；暂停/恢复：`slk-pause-run`；D2 与结束收尾若拆分，各有唯一权威入口且保持原先后关系。
- 主 Skill 只给跨角色的最小全局边界和链接。必要的安全短句可留在动作现场提醒，但不复制整套细节；一条规则不能在多处各自演化成不同版本。

## 3. 角色按当前情境读取

- Supervisor 理解主 Skill，在规划、团队准备、FAIL、暂停或 D2 到来时读取相应子 Skill；不要求平时在线逐 CELL 盯工。
- Worker 在施工时读取执行 Skill 和当前 CELL；资源阻塞等真实发生时才补读对应参考，不加载 OW/Temporal 运维手册。
- Checker 派发时读派发、检查时读 D1；FAIL 时沿既定返工通路。平台没有任意 Skill 加载能力时，由既有宿主注入当前必要指引，不伪造“Agent 已加载 Skill”。
- OW 读观察 Skill 和实际状态/证据入口；10 分钟主动巡查、Temporal 20 分钟核验、成员停留 30 分钟提醒、退出二次确认及多 Run 隔离保持原语义。
- 其他成员收到的是当前职责、当前任务与必要边界，不是一份手工维护的全量规则副本。控制消息继续用材料位置/字节数/哈希；不增加字符或读取硬上限。

## 4. 先核对可靠性，再去重去繁

先建立短的旧规则→唯一权威位置对照，再逐块替换。每项归类为：保持原语义、迁到按需参考、删除重复、或 Owner 已批准的轻量准备/OW 直属 subagent 调整；不能以“精简”为由偷偷放宽权限或工程验收。

重点排查：重复 gate、从一次故障泛化的数字门槛、相互引用形成的循环、同一状态多个解释、过期修复步骤仍被描述为当前默认路径。真正的原生平台限制、身份约束与必要安全边界保留并注明来源；无依据的统一容量/篇幅/时间配额不保留。

负面提示词放在最容易犯错的子 Skill，使用具体动作与后果；主 Skill 保留全局越权、伪造事实和错误通讯流的禁令。不堆积历史事故清单，也不通过删除所有禁令来凑缩减数字。

# 第三步：工具模块化、独立 Git 与源码/成品 subtree

## 1. 仓库与版本规则

- 每个实际工具有独立 Git；先核实已有独立库及版本线，已有则沿用，不重建替换。新建工具库从 `1.0.0` 开始；已存在工具的产品版本与历史不因抽取 Git 倒退，台账区分仓库首发 tag、工具产品版本和 SLK 方法版本。
- 按可独立安装/使用/发布的工具划界，不把每个脚本、共享内部库或 adapter 文件都拆成独立产品。盘点 BI/WebBI、状态、查询、Cargo、transport、Temporal/DSH/OCRV 配套、OW 工具与原生探针的实际依赖；BI/WebBI 保持同一工具版本线，上游 DSH/OCRV/Temporal 既有库、许可证和版本不擅自另造或重置。
- 主 SLK 库使用真正 subtree 纳入各工具的源码、构建规则和经过验证的编译成品，而非只放外链、submodule、旧安装文件或 Release 链接。优先保留可用目录和公开命令；确需迁移时一并修正构建、导入、安装、文档及测试调用，不留下第二份手工同步源码。
- 复用现有 Manifest/构建清单记录“工具库 + 精确 commit/tag + 主库 subtree 前缀 + 成品路径/平台/版本/hash”；main 使用已验兼容的明确版本，不在使用者启动时浮动追踪各工具最新 main。
- 第三步抽取的是第一、二步完成后本次 4.5.0 实际采用的最新源码。工具被 4.5.0 修改过就重建对应成品、核验来源并按自身版本线记录；只更新源码或版本文字、继续打包旧 exe/pyz 不算完成。

## 2. OW 与探针的明确模块边界

| 部分 | 唯一权威归属 | 交付与运行方式 |
| --- | --- | --- |
| OW subagent 规则 | 主库 `skills/slk-overwatch-run`，仍逐份确认 | 由 Supervisor 启动的唯一直属 OW 主动执行，覆盖该 Supervisor 全部 Run；不是独立组队角色或编译成品 |
| OW 配套工具 | 独立工具库 `slk-overwatch-tools`；核实已有独立库则沿用 | 从既有实现提炼可独立测试的核验/巡查辅助，预打包；保留原公开入口与权限，不新增常驻服务 |
| DSH/OCRV 原生探针 | 独立工具库 `slk-native-probe`，内部两种宿主适配 | 原生 hook/读取器、紧凑存储与查询同一模块维护，嵌入既有宿主、同一安装入口部署；不是可选的代码检索工具 Probe CLI |
| 权限、工程事实与计时 | 原状态/transport/Temporal 的相应权威入口 | 不迁出 TOKEN/D0/D1/D2/角色权限，不另建中央状态或调度器；Temporal 的 20/30 分钟计时不复制到 OW 工具 |

独立维护和发布不等于独立常驻进程。通用核验消费明确来源的输入/收据，平台连接沿登记 adapter；共享合同/身份校验只有一份权威来源，不将 native-start 核心生产/验真复制到各库。抽取时避免 `transport ↔ OW 工具 ↔ 探针` 互相导入私有实现或维护多份平台连接；优先保留现有命令及数据兼容，只加必要的内部边界。

**OW 不变的职责：** Supervisor 的唯一直属 OW subagent 在真实 active 运行中每 10 分钟核对、报告矛盾/异常/未知；只向所属 Supervisor 报告，不代发/恢复/施工/验收，不写 BI、TOKEN 或工程进度，仅沿原权限追加自己的观察。报告后继续，所属 Supervisor 各 Run 分别关联 scope/原消息/证据；退出通知与 Supervisor 二次确认、Temporal 独立核验继续有效。工具安装不自动创建 OW、选择模型或绑定 Run，也不新增 heartbeat、计划任务或独立后台 Agent 替代它。

**统一探针交付要求：**

- 采集不按 Run 开关或只盯某一个 Run：覆盖目标工具原生可查询的非归档 Session/任务，在宿主工作期间采用该工具统一的一分钟采样，不因多 Run 或重复安装倍增计时器/全量扫描；宿主原有事件记录照常，查询不重新触发整工具采样。退出/终态沿原生事件留证，宿主停止后显示真实离线与最后观测时间，不虚构新采样/在线状态，也不为探针启动额外 Agent 或常驻服务。
- DSH 归档排除只认其原生 marker；OCRV 在采用版本无可验证归档标记时不猜归档、不因 BI 不显示而跳过。覆盖范围或原生能力不足要明确暴露，不默记“已完整采集”。每个对象保留设备/宿主实例/原生 Session或任务/进程创建身份、采样时间与最后原生事件时间等实际可证事实；某 Run 的关联由登记与原消息/native start 精确匹配，不能用另一 Session 活跃掩盖其停工。
- 每工具 10MB 是采集后紧凑观测的总持久化预算（含索引及写入所需空间），不是每个 Run/Session 各 10MB，也不是原生日志或资料读取上限。采用紧凑最新状态与短事件保留，更新不无限追加、不复制对话/推理/工具参数结果或整段日志；只暴露必要元数据和原件定位。容量/覆盖不足明确 UNKNOWN/缺口，不静默漏掉对象再声称正常。
- 原生未确认、陈旧、冲突或访问失败均保留真实原因，不由模型自报补齐。PID/进程存活、原生任务状态与最后事件可以交叉核对，但“存活”不等于有工程进展；需要时仍可读取原件。OW 只取本轮必要小摘要及证据位置，不把 10MB 整包放进上下文。
- 一键部署与 BI 同入口、headless、保留原生配置和数据、重复可用、失败可回滚；无需每 Run 安装或用户手改源码。JS/Python 插件按已验证可执行包交付并准备必要宿主依赖，不强行为每个插件另造 EXE 或运行服务。
