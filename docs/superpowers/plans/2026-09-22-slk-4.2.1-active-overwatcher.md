# SLK 4.2.1 Active Overwatcher Implementation Plan

**Goal:** Replace the withdrawn 4.2.0 event-woken observer semantics with one mechanically bounded, foreground-active Overwatcher Agent Session while preserving the original SLK engineering topology.

**Constraints:** No heartbeat, automation, cron, Scheduled Task, daemon, service, detached helper, background Agent, second observer, new engineering role, TOKEN authority, or direct BI mutation.

## Task 1: Freeze the semantic regression

- Add Skill/eval negative cases rejecting end-turn observation, passive wake dependence, heartbeat/scheduled-task/daemon substitutes, missing fixed checklist, cadence outside 180–300 seconds, and a second observer.
- Add positive cases for one continuously active Session, a complete 240-second cycle, event-accelerated inspection, quiet normal cycles, and terminal archive.
- Confirm the new tests fail on 4.2.0 behavior.

## Task 2: Add the minimal state contract

- Add one schema migration for versioned Overwatcher cadence/binding facts and append-only observation cycles.
- Extend binding with interval, foreground-turn capability, and native active-session evidence.
- Add a closed cycle request and CLI command; validate monotonic sequence, complete checklist, current plan/scope, evidence, non-overlap, and same bound Session.
- Project only the latest accepted cycle health to the read-only BI query.

## Task 3: Enforce active-session boundaries

- Reject active claims based on free text, an old event, task visibility, heartbeat, automation, or scheduled wake.
- Require the Overwatcher Skill to keep its current foreground turn open and perform the next cycle itself after a bounded 180–300-second in-turn interval.
- Block new dispatch/handoff when a bound Overwatcher has two consecutive overdue cycles or lacks foreground-turn proof; do not interrupt in-flight work and do not affect Runs with no Overwatcher.

## Task 4: Replace documentation instead of adding method weight

- Replace defective 4.2 wording in README, main Skill, Overwatcher Skill, state/BI/transport/runtime references, templates, migration, and changelog.
- Mark 4.2.0 `WITHDRAWN / DO NOT ENABLE`; bump the candidate to 4.2.1.
- Keep Supervisor/Checker/Worker communication, CELL, D0/D1/D2, rework, TOKEN, BI authority, and headless helper rules unchanged.

## Task 5: Validate and package

- Run focused Rust/Python/eval tests, then full repository, state, transport, BI, package, manifest/hash, mirror, version, sensitive-data, boundary-word, and diff checks.
- Build and deploy only after all gates pass; preserve a rollback backup and keep helper launches headless.
- Do not push, tag, create a Release, or start an LCaS successor Run without the separate authorized acceptance step.
