# SLK 4.4.0 State Core

SLK uses one configured machine-wide data root for structured Run state, evidence, operational observations, and deterministic Markdown exports. Project repositories remain unchanged. SQLite is authoritative; `SLK-RUN-<RUN-ID>.md` is a regenerated view.

## Interfaces

- `slk-state configure --data-root <absolute>` selects the one data root and initializes its empty versioned database.
- `slk-state init-run --request <json> --credential-out <directory>` initializes a Run, records an explicit predecessor when this is a successor, and writes sealed role credentials without exposing them to another role or ordinary shell output.
- `slk-state reconcile-run-identities --request <json>` lets the canonical Run's current Supervisor archive only the explicitly named historical roots after exact snapshot and closed Owner-evidence validation; it appends one immutable reconciliation receipt.
- `slk-state adopt-method-contract --request <json>` supports declared adjacent transitions through `4.3.6 → 4.4.0`, preserving `origin_slk_version`, TOKEN and engineering history. Installing or adopting does not start Temporal, resume a Run or modify product files; 4.4.0 readiness separately requires the current four-role registry, BI, Temporal and communication receipts.
- `slk-state bind-overwatcher`, `record-overwatch-cycle`, `record-overwatcher-status`, `resume-overwatcher-turn`, `replace-overwatcher`, `rotate-overwatcher-credential`, `record-observation`, and `close-overwatcher` maintain exactly one required whole-Run OW binding, revision-bound cycles, native status and explicit continuity transitions for a ready 4.4.0 Run. One exact active Session may have distinct bindings for multiple Runs only when its agent/runtime/model/endpoint/cadence facts match. `resume-overwatcher-turn` and stop/repair decisions are Supervisor-only; OW never edits engineering state. `wait-for-change` is a bounded read in the same process, not a scheduler.
- `slk-state register-role`, `replace-role`, `rebind-session`, `revise-plan`, `write`, `register-evidence`, and `commit-delivery-start` are authenticated mutations. `commit-delivery-start` atomically records verified start evidence, advances TOKEN, appends `TRANSPORT_STARTED`, and stores one runtime snapshot; legacy `handoff` remains only below the revisioned runtime contract. Exact 4.2.4+ Worker event replay is idempotent, while a reused event ID with different content fails closed. After the terminal Run event exists, `close-role --request <json>` lets the current Supervisor retire the exact Checker or Worker without a successor: one transaction appends `ROLE_CLOSED`, retires the endpoint, revokes its credential, sets lifecycle `exited`, and preserves TOKEN plus all D1/D2/closure facts. `authenticate-role` performs a read-only exact credential/role check and returns only role identity plus current runtime revision. Credentials are supplied only through `SLK_ROLE_CREDENTIAL`.
- `slk-state export --run-id <id>` and `verify-evidence --run-id <id>` require an active role credential.
- `slk-bi-query projects|runs|run|graph|roles|plans|events|evidence` opens SQLite read-only for one invocation. It has no mutation or credential surface.

Supervisor, Checker, and Worker write only the engineering facts owned by their existing SLK boundaries. Checker owns D1; its standard OCRV tool internally authenticates the sealed Checker credential and binds candidate message, v2 start, terminal identity, result SHA-256 and aggregate evidence before recording D1. Supervisor/Overwatcher/shell cannot substitute. After exact `D1_FAILED` escalation and TOKEN transfer, Supervisor alone may append `REWORK_REQUESTED`. A bound Overwatcher appends only complete cycles and operational observations; it cannot hand off TOKEN, write D0/D1/D2, change plan/role, set acceptance or close the Run. Owner, BI and other Agents query only. Only a hash-verified `slk.native-start/v2` receipt qualifies for `commit-delivery-start`; legacy start, database row, terminal result, launcher exit or old message never proves delivery.

## State behavior

Every Run has one monotonic TOKEN history, one current plan revision, ordered CELL definitions, complete role-instance history, append-only work events and hashed evidence. Schema v9 permits one exact OW Session to carry distinct per-Run bindings without merging scope; each 4.4.0 cycle must match its Run/binding/turn, current runtime revision, fixed 600-second cadence, checklist and verified evidence bytes. A projected active role does not prove a fresh cycle. OW reports `ANOMALY`/`UNKNOWN` to Supervisor and continues observing; it never performs recovery. Normal close uses the exact `D2_PASSED` snapshot for the final cycle and Supervisor-confirmed `close-overwatcher`, then records `RUN_CLOSED`. Planned archival or absent native Session is never reported as actual archival without central evidence. The core creates no heartbeat, scheduled task, daemon or background Agent.

Run identity is explicit. A successor names its predecessor; one lineage head is current, predecessors are history, multiple active heads are `DUPLICATE_ACTIVE_RUN`, and unverifiable lineage is `ORPHANED_IDENTITY`. Separately initialized roots become a valid canonical/history set only through a matching immutable reconciliation receipt whose stored pair still agrees with current metadata. Titles, project names, and timestamps never merge Runs. Schema v8 keeps origin/effective versions, administration receipts, transport starts, runtime snapshots, native-status facts, continuity incidents, binding transitions and credential-rotation receipts append-only. None rewrites work events, roles, TOKEN, evidence, CELL state, D0/D1/D2, or plan history. `working` is derived from current accepted evidence, never a stale chat status, TOKEN holder, cadence timer, heartbeat or BI process.

## Lost Overwatcher write credential

`overwatcher_credential_id` is non-secret metadata and cannot authenticate; only the one-time `overwatcher_write_credential` value beginning with `slk_` is usable. If the complete secret was lost or its ID was stored by mistake, do not fabricate a cycle, mark a continuity violation, replace the Session, or edit SQLite. The current Supervisor submits the closed [`slk-overwatcher-credential-rotation.schema.json`](../contracts/slk-overwatcher-credential-rotation.schema.json) payload with the exact current binding/runtime/role/Session/turn/credential ID and hash-verified evidence:

```text
slk-state rotate-overwatcher-credential --request rotate.json
```

Capture `overwatcher_write_credential` from that one non-replayable response, immediately verify it with `slk-state authenticate-role --run-id <run> --role-instance-id <overwatcher-role>`, and never substitute the returned `overwatcher_credential_id`. A stranded 4.2.7 Run rotates first under its current contract, records the first valid cycle with the same binding, then adopts 4.2.8 using a fresh exact snapshot and `PRESERVED_ACTIVE`; the rotation itself does not invent continuity evidence.

An effective 4.2.8 through 4.3.6 Run whose exact current binding is already `VIOLATION` may use `resume-overwatcher-turn` with `last_native_status_id` instead of `last_anomaly_cycle_id`. Each native pause creates a distinct append-only incident keyed by that exact status receipt; the matching resume resolves only that occurrence, so later pause/resume cycles on the same binding cannot collide. The receipt must be the latest non-`IN_PROGRESS` status for the same binding revision, role, Session and old foreground turn. A valid Supervisor request supplies a fresh runtime revision, a different new turn and hash-valid active-session evidence; it preserves the binding identity, restores `ACTIVE`, appends `RESOLVED` to the exact incident and advances runtime once. A replaced binding, older status, both/neither basis or ordinary cycle during `VIOLATION` fails closed.

Successful writes attempt to refresh the Markdown export. An export warning does not undo an already committed SQLite fact; rerun `slk-state export` after the output path is available.
