## 组织方式：两项独立交付，必要接口一起核对

推荐：BI 与 4.x 各自实施、测试、发布，只协调共同读投影和模块版本。BI 不必等待全部 4.x 维修完成；4.x 不能把 UI 修正包装成状态机修复。

没有采用的两种做法：

- 合成一个大版本同时改：读投影、运行修复和 UI 故障容易互相掩盖，回退也会捆绑。
- 只改文案/增加容错绕过：能暂时减少报错，却会保留错误身份关联和失真的停止判定，不能作为正式修复。

允许在原模块内消除重复判断、复用同一次观测；不新增中继、常驻同步器、审批器或监控角色。工程回归留在开发/发布阶段，不搬进每次 Run 预检。

## 一、BI/WebBI 1.1.3

### B1. 数量格子与拆分说明

1. 复用现有有效 CELL 口径：拆分父节点保留历史，但不重复算进有效总数。
2. 0 个不画虚构格；1–30 个按真实数量画，每行最多 10 个、最多三行；末行不补齐、不拉伸。
3. 超过 30 个只压缩格子概览，不压缩数据。精确分子/分母和符合现有显示条件的全部详情继续保留；未全部完成不能把比例格填满。
4. 进度旁显示初始数量及拆分净增：初始 3，拆一成二后为 `0/(3+1)`；一拆三则增加 2；嵌套拆分按有效净增累计。
5. 普通追加/移除不能被伪装为拆分。只有历史完整、能证明该分解与当前有效总数一致时才显示加法；否则显示准确总数，不能反推一个虚构初始值。

具体接入：当前 `RunStrip.tsx` 的 8/16/24 补齐逻辑与对应测试一起替换。当前数据库已保存初始计划 `snapshot_json` 和正式 `CELL_SPLIT` 事件，但 BI 的计划投影只暴露修订元信息，不能假定前端已经拿到初始计划。

建议在现有只读查询中提取最小的计数依据/摘要，交给共享展示逻辑，不把完整计划原件上传给 WebBI；不新增持久计数表，不让 BI 回写计划。优先利用已有事件和快照，历史无法确定时保留缺省，不为这项显示做数据库写入迁移。新增投影字段需要兼容旧上传，不能让旧桌面 BI 立即失效。

已核实的 Run09 `3 → 4` 是一次正式拆分的正确有效总数；问题是格子补成 8 个，不是“未同步”或“应该算 5 个”。这条事实纳入回归样例。

### B2. 背景透明度滑条

- 在现有齿轮设置内将下拉框替换为标准滑条：0–100%，步长 1%，显示当前百分比，点击、拖动、键盘与触摸均可操作。
- 只改变背景/框体颜色的 alpha；文字、图标和控件不使用整体 opacity。删除 Owner 指定的解释文案及同义冗余提示。
- 延续既有本地设置；未保存时仍使用原默认值，显式保存的 `0` 必须与“没有保存”区分。不能因 `Number(null)` 得到 0 而把新用户默认值改掉。
- 100% 时齿轮、滑条、焦点和点击区域仍存在；透明背景不等于鼠标穿透或隐藏整个窗口。WebBI 只透出网页底色，不控制浏览器窗口。
- 不添加收缩/展开高度动画，不改成复杂自绘控件，不改现有整体配色或桌面密度。

### B3. 保持已修好的行为

- 桌面为数据来源，WebBI 只消费桌面上传投影；共享计数和状态展示逻辑，不再各写一套。
- 未开工 CELL 详情不显示，但属于有效计划的仍计入总数；最新活动在上；只允许一个 Run 展开。
- 外层主 Run 滚动和内层最多六行 CELL 滚动继续独立，展开不消耗主列表的五个 Run 标题额度，收起直接缩回。
- 正常工作使用绿色；排障、明确等待等特殊状态有事实才显示。BI 不能凭 TOKEN 持有人推断“真正在工作”，不能将 UNKNOWN 改成绿色遮掩故障。
- 未读绿点及 ntfy 只消费 Agent 标注的正式消息。更改透明度、刷新或新增计数字段不会制造新的通知。
- 保留电脑身份、BI 版本、角色身份、归档、移动端浏览器适配；不重新引入查看登录或改变通知权限。

### B4. 边界与验证

本次不做 3.x 工作簿读取器、不规范化 3.x 工作簿、不改 3.x Skill 或部署。通用兼容目标保留至 3.1.0 恢复后策划；不能宣称 BI 1.1.3 已自动支持所有未知格式。

兼容现有受支持的只读 SQLite 数据格式；更新实际需要的 BI 上传版本声明，不用 SLK 方法版本作为显示白名单。方法启动收据中如有阻止新版 BI 的补丁号枚举，归入 4.x 的小范围配套调整：验证产品能力/真实身份，不能直接删除全部校验。

开发阶段验证：

- 格子：0、1、4、10、11、20、21、30、31、100 个；部分完成/全完成；大于 30 不影响规划、存储、派发和详情。
- 历史：初始计划、一拆二、一拆三、嵌套拆分、非拆分增减、缺少初始快照；只有有依据的情况显示 `初始+净增`。
- 滑条：0、1、37、99、100%；无保存值、旧值、存储不可用、关闭设置和重启恢复；文字/图标不随背景变透明。
- 两端：同一只读样例得到相同计数和次序；旧上传继续可读，新字段缺省不丢整个 Run；消息类型和 ntfy 行为不被 UI 修改污染。
- 集成：前端测试、类型检查、生产构建；如读投影改变，增加 Rust 查询及上传契约回归。实际 Windows 窗体的透明/点击/高度效果需在预编译成品上核对，不能用组件测试冒充；遵守 Owner 的不用 Computer Use 要求，保留原生非 UI 诊断及 Owner 截图验证的区分。

## 二、4.x 实战问题维修

### 七类问题如何落地

| 编号 | 要纠正的错误 | 最小修法与证明方式 |
| --- | --- | --- |
| R1 | OCRV 在模型工作前因 8000 字符门槛拒绝材料 | 沿 SLK adapter → 实际 OCRV 入口查清哪层拒绝；删除已证实的任意附加门槛，不换成更大的固定数。原件引用可减重复背景，但必须实际能读完整原件；覆盖本轮 10413 字符及文件外部读取。原生版本仍有约束时明确指出，不以改 SLK 常量冒充彻底解决。 |
| R2 | 合法恢复仍按失败的原启动、或把历史计划按当前计划核对 | 使用原调用与已授权恢复之间的明确关联；历史 Host 用原计划/Session/任务身份核验，当前责任用当前登记。补同 Session 跨合法计划的正例，保留错 Run、错 Session、错候选/hash 的拒绝反例；禁止重写历史让它“匹配”。 |
| R3 | OW/Temporal 反复出现同类失败，解绑后还收到审计 | 先取原工作流事件，区分旧消息迟送、旧绑定残留与新审计。沿既有绑定/投递/结束入口修真正的问题，不笼统吞掉重复告警。关闭只针对准确 Run 的工作流 pair，保持共享服务及其他 Run。现有 CLI 已能正常关闭准确 pair，不重造关闭器。 |
| N1 | 申请暂停还未生效，却不能撤回 | 核对并吸收现场最小 REQUESTED 撤回改动，保留 pause_id/revision、权限和原 TOKEN 归属；不伪造 PAUSED，不扣除并未暂停的时间。覆盖撤回幂等、旧信号迟到、已经 PAUSED 的正常恢复，以及原 Temporal 历史回放。 |
| N2 | OW Skill 教它写消费者不接受的字段，并混淆自身和被观察者 | 修改原 OW 子 Skill 的语义和紧凑示例，让例子直接通过真实消费者。OW 自己活跃与被观察 Worker/Checker 状态 UNKNOWN 可以同时成立；不增加第二层解释器、不放宽所有 schema。 |
| N3 | 多条通知指向同一个 Supervisor 回合，却被当成多项未停止工作 | 按精确原生调用身份归并别名；只把当前真实协调回合识别为协调，不豁免所有 Supervisor/历史写入者。同一次检查复用同一原始观测及时间，避免重复读取历史；失效、失败观测仍保持 UNKNOWN。 |
| N4 | OCRV 自己产出的原生状态不符合自己使用的消费契约 | 修 inspector 与 TASK_ACTIVITY 之间的现有投影接缝，完整保留身份、关联与取证时间。用真实输出作样例；launcher 结束但 executor 仍活跃必须不能判 STOPPED，报告文件存在或 transport FAILED 也不能作为停机证明。 |

### 实施顺序与原模块边界

1. 固定失败样例和真实消费者，逐项确认哪段正式源码与现场临时修正不同。找不到现场副本时重新构造明确的小复现，不把未知补丁直接合入。
2. 先处理 N4 状态投影和 R2 恢复身份，再处理依赖它们的 N3 收尾判断。这样不会用错误输入去优化关闭流程。
3. R1 材料入口、N2 OW 指引各自独立验证；N1 暂停撤回复用现有实现；R3 在拿到事件链后决定是否以及改哪段代码。
4. 组合回归：真实在运行的不能被误报停机；合法恢复不能被旧失败挡住；重复通知不能重复算成员；结束某 Run 不影响另一个 Run。主管保持在线参与收尾，不要求“先退出，再由 OW 叫醒”。
5. 更新相关原 Skill 的少量操作示例与负面提示，不复制一套新治理规则。Supervisor 的现场补漏和记录责任仍在，不能将小故障都等待源码升级。

预期主要触点：

- `src/slk_transport/adapters/ocrv.py`、`native_activity.py`、`role_host.py` 及原恢复关联入口；原生 OCRV 修改必须先核实对应源码和预编译载荷版本。
- `crates/slk-state-core/src/write.rs` 的暂停生命周期及相关回归。
- `integrations/temporal/src/slk_temporal/` 的既有工作流/信号/绑定与结束路径，按事件证据确定实际修改文件。
- 原 OW、恢复、暂停、关闭子 Skill；仅改职责表达错误或操作缺口，不扩张角色权限。
- BI 新版本收据兼容是配套小改，不成为第八类现场故障，更不借机增加 3.x 运行底座。

### 保留未知，不用一条规则抹掉

现场 76 行 UNKNOWN 是不同来源的证据，不是 76 个 Agent，也不是一种根因：40 条 MCP 失败、5 条投影不匹配、2 条端点不可读、19 条历史启动/停止缺证、6 条原调用 active/unknown、4 条 stale。

- N4 直接覆盖投影不匹配，不因此声称 MCP 或端点也已修好。
- MCP/端点问题逐类看请求参数、路由、权限及响应；audit83 看原产生与送达时间。没有证据前不归咎“旧别名”或“工具不行”。
- 历史无证据、观测过期继续明确标注缺证，不能批量改 STOPPED；需要现场处理的交由原 Supervisor 决断并记录。
- 不把 LCaS 产品自身 D1 失败、Windows 中断或成员自行用错命令计为已确认 SLK 缺陷。

### 维修验证与结果报告

每类修复提供：原失败样例、最小差异、修复后结果，以及不能被放宽的反例。重点复用现有 transport、native activity、role host、pause、OW 和 Temporal 测试；暂停涉及持久工作流时回放真实历史。

验证在独立样例/测试工作流中进行，不往正在工作的 Run 写假事件、不替它发送消息、不重复 D1/D2、不重开已结束 OW。现场 Rust 38 项、Temporal 4 项及回放为原报告证据，正式交付时必须说明哪些重新跑过，不能挪用为本次全绿结果。

## 三、发布、部署与不扰动原则

- 两项分别有版本/变更清单、回归结果和预编译产物；共改 state-core 读投影时对齐同一小改动，避免相互覆盖或发布不匹配的库。
- 保持现有独立模块仓库/subtree、源码提交与成品哈希一致。修改了什么模块就重建并更新该模块成品；不把未验证的工作目录复制为安装版。
- BI/WebBI 配套 1.1.3：若上传契约增加字段，先验证云端兼容新旧投影，再切换桌面成品。部署故障时可回退成品，不回写或倒退 Run 事实。
- 成品在工程发布阶段编译，用户或 Supervisor 启动 Run 直接使用；不在开工准备时临时构建 BI/OCRV/Temporal。
- 只制定部署步骤，不在本轮策划中 push、release、替换本机程序、清理旧版或改云端。后续实际部署需避开正在使用的绑定，确认目标版本和产物；不能为清理旧版删掉在用运行时、回退必需成品或工程记录。
- 3.1.0 的恢复时间与接入方案留待该线工作完成后另行安排；本轮不联系或重配其成员，不把 BI 兼容目标误报为已接入。

## 四、自检结论

本稿仅约束两项工程的范围和最小改法，不增加 Run 材料/时间/规模硬门槛。30 格是 UI 上限；100% 是显示偏好；缺证状态不是 PASS/STOPPED。七类实战问题与未定因现象分开，4.x 版本号未擅定，3.x 工作不受影响。

确认方案后再形成逐模块施工步骤。当前没有任何修复、测试通过、发布或部署完成的声明。
