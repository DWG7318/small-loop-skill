## 建议处理顺序

P0先做且保持最小施工：第一，给 TOKEN/event/message 引入同一只读 snapshot revision，消除 Overwatcher无法组成新鲜 cycle 的根因；第二，把 DSH/OCRV启动证明从 terminal读取中分离，只有真实 started 证据后才允许 TOKEN交接；第三，为 Codex active-writer建立闭合、可审计且不重放旧 envelope 的恢复分支；第四，在派工前门禁 Git common dir 可写性，默认隔离 Worker使用 standalone clone。

P1跟随对应 adapter和部署边界完成：使用哈希绑定的 task file、统一短 instance ID、冻结 canonical Owner输入来源与 fresh native liveness、把全局 docs/schema纳入安装一致性。P2只增加紧凑指标和软预算，不引入新的调度层、heartbeat、后台 watcher、BoM或自动模型切换。

## 下一版本必须先失败的八个验收反例

1. **晚启动证明**：模拟 DSH/OCRV 已生成 terminal result、但30秒内没有 `started.json`；系统必须拒绝 TOKEN交接和完成声明，不能事后用 terminal补写启动。
2. **活跃 Supervisor writer**：目标 Supervisor正在写回复时投递 Checker escalation；系统必须通过一条新的、可审计的 native message identity恢复，不能重发旧 envelope、重复 TOKEN或创建替代 Supervisor。
3. **跨 revision 投影**：token为 T(n+1)，event/message仍属于 revision n；Overwatcher必须拒绝组合该快照，而同一 revision 的三者必须一次读取成功。
4. **不可写 Git common dir**：Worker workspace可写但 linked worktree `.git` 在沙箱外；容量/派工门禁必须在启动前拒绝该形态或改用 standalone clone，合法任务中 Worker应能直接提交。
5. **长参数任务漂移**：命令行含完整长 envelope但 task file缺失或哈希不符；Worker不得搜索旧 Run/旧 message猜任务，adapter必须 fail closed。合法 task file只用短参数即可完整恢复固定身份和结果路径。
6. **超长 instance ID**：长 Run ID生成超过64字符的 DSH instance ID；transport必须在启动前稳定拒绝。合法生成器必须得到不超过64字符、仍可机械证明 Run归属且两侧校验一致的 ID。
7. **历史指令与假死亡**：source Run有更新的时间戳文本，但 canonical binding revision之后没有对应 Owner指令，同时原生 foreground turn返回 fresh active；Overwatcher不得采用 source文本，也不得记录 inactive/degraded。
8. **安装身份漂移**：candidate skills/binaries为目标版本，但全局 state docs、transport docs或schema仍是旧版本；部署门禁必须拒绝完成。全部安装面版本与哈希一致时才允许通过。
